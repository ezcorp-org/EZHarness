## The guest program shape W10 and W11 implement — migration note

The shape is a real program, not a description: `GUEST_PROGRAM` in
`src/factory/runner/guest-model.podman.integration.test.ts`, which runs under Podman in G6. W10's
generator and reviewer and W11's evaluator implement exactly this.

1. **Read the pin off the request, never from anywhere else.** `request.model` is a
   `FactoryModelPin`. An attempt with no pin may call no model: the guest fails rather than
   picking one, and the host refuses it anyway.
2. **Build the operation identity from the authority.** The id is
   `runId:nodeInstanceId:candidateGeneration:index`, and the first index is
   `authority.nextOperationIndex`. The host checks this against the journal, so an id the guest
   invented is refused rather than journalled.
3. **One call per operation.** Increment the index for the next call. Calling the same operation
   twice is refused `operation_settled`, and two at once are refused `operation_busy`.
4. **Send one frame over `context.call('factory.broker', …)`.** The payload is a
   `FactoryGuestModelRequest`. This is the one reverse capability; a payload whose `schemaVersion`
   is not `factory.guest-model-request.v1` goes to the broker's delegate, which is how the
   validator report frame still works.
5. **Read one `FactoryGuestModelResponse` and branch on `status`.** A `refused` answer is an
   outcome with a typed `refusal.code`, not an exception and not a reason to retry. There is no
   fallback model.
6. **Never retry and never truncate.** The host already refuses an answer too large for the frame,
   after recording what it cost.

Bounds a guest must respect, from `FACTORY_GUEST_MODEL_LIMITS`, measured in BYTES not characters:
64 messages, 16 KiB per message, 32 KiB of input, 1 to 8192 output tokens, 128 KiB of response.

## What I did not do, and why

- **The journal write needed no new method on W03's file.** I expected to file a request. The
  four calls the tool path already uses are enough, and using them means a model operation and a
  tool operation are one kind of durable effect rather than two.
- **The workspace checkpoint is injected, not invented.** A completed settlement must carry one,
  and `FactoryWorkspaceCheckpoint` in `src/factory/runner/supervisor.ts` already declares the
  seam. `createFactoryJournalGuestModelJournal` takes it as an option; W04 supplies it.
- **`createFactoryMemoryGuestModelJournal` is named for what it is.** Nothing in it survives the
  process, so no product path may use it. It exists for fixtures and keeps the same one-winner
  rule so the guest-visible contract is identical.

## Lessons

- **An optional parameter cannot express "absent".** `attempt(undefined)` took the default and
  silently produced a PINNED attempt, so the unpinned case passed against the wrong input and then
  failed for a reason that looked like a product bug. The helper now takes `null` for "no pin",
  and the test proves the attempt is unpinned before asserting the refusal.
- **A durable claim is not the same guarantee as an in-memory one.** The first broker used a `Set`
  keyed by attempt and operation. That cannot refuse a caller in another process, and the host
  supervisor and the product process are two processes. Replacing it with `prepare` then
  `dispatch` also made a test assertion wrong in a useful way: an operation that settled can never
  call again, which the in-memory version allowed.
- **Record the cost, then answer.** The ordering is the contract, so it is asserted by holding the
  recording open and proving the call has not resolved, rather than by reading a list afterwards.

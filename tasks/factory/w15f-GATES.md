# Gates: W15f stale execution epoch hold

Scope: the team lead's W15f assignment (2026-09-27). Branch `wp/w15f-stale-epoch` from `integ/w00` at `29f8f2d4b`. Evidence under `/tmp/factory-platform-evidence/w15f/`.

Finding: the fault was usage reconciliation, not a restore or stop role. `w01i/logs/lane2-processes/web.log` holds 15 reports of `usage-reconciliation:fault:factory-reservation:98ddd419...` with "FactoryAttemptLivenessError: Factory run epoch is stale or unavailable.", after many `transient` (no-operation-receipt) reports of the same reservation. The lane's restore case (test 12, left unsigned) opened a restore epoch; `FactoryRestore.openEpoch` moves the installation's execution epoch at once, and runs move only on signature. Reconciliation resolves a hold through `journal.operations(sealed authority)`, which takes `lockRunFence`; the sealed authority names the old epoch forever, so the fence refused on every pass and the scan listed the hold again. The mark is on the hold, not the run: a signed restore rebinds the run into the new epoch and the run lives on; only the old attempt's authority stays behind.

- [x] G2: The fix (the lane's 15 reports per run become 1 per hold per epoch).
  `lockRunFence` raises `FactoryRunEpochStaleError` (a `FactoryAttemptLivenessError`, same code and message) with the run, the attempt, and both epochs. The usage-reconciliation step marks the hold once (`factory_budget_reservations.epoch_stale_json`: attempt, attempt epoch, installation epoch, time; migration `add-factory-usage-epoch-stale`, mirrored in `factory-schema.ts`) and reports one `FactoryUsageHoldEpochStaleError` (`factory_usage_hold_epoch_stale`) naming the reservation, run, attempt, and both epochs. `listUncertainWithCostInTransaction` skips a hold marked at the current installation epoch. The hold stays `uncertain`. A hold that settled before the mark is not marked, and its refusal is reported as it came.
  CHECK: the reproduction suite on PGlite and PostgreSQL; the driver unit cases; the migration test
  EXPECT: one report over four passes and a restart; none after the signed restore; one more after a second restore; the durable mark names both epochs; the live hold keeps its transient retries
  EVIDENCE: commit `6a160c81e`. The pre-commit hook ran all 6 mapped files, 0 fail (`logs/commit-hook.log`); the first attempt failed on real PostgreSQL only (`logs/commit-hook-attempt-1.log`: after a second restore the hold was never reported). Cause: the mark was written as a text parameter cast to jsonb, which reached PostgreSQL as a JSON string; `->>'installationEpoch'` was NULL and `NULL <> epoch` hid the hold forever. The mark is now built with `jsonb_build_object` from typed values, and the scan compares with `IS DISTINCT FROM`, so an unreadable mark is retried and reported. A new case stores a JSON-string mark and proves one report; it fails on the old comparison. The suite asserts `jsonb_typeof = object`.

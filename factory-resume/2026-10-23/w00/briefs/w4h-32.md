# W4H-32 — runner store resilience: a missing release artifact is rehydrated from the product's own copy (owner: w4h-32; coordinator-added 2026-10-15 23:2xZ)

## Where it stands

- W4H-28's real-8 pass failed on a reused installation because the extension runner's store had lost the only release artifact of `@ezcorp/reference-code` (built into an earlier runner store that a cleanup removed). The runner answered a plain ENOENT, which W4H-28 now names `artifact_missing` (commit 2a0c65e74 on `wp/w4h-28-reference-run`; the runner returns 500 `runner_internal_error` for other unclassified errors through the shared error shape in `@ezcorp/extension-contract`).
- The product keeps its own copy of every built release in its blob store (worktree `.ezcorp/extension-releases`; `extension_release_records` names the release and its digest). W4H-28 worked around the gap in the proof harness only (a kept deployment keeps its runner store). The product itself still cannot recover.
- Evidence of the failure: `evidence/w4h-28/proof/real-8.*`, `legs/`, `red/`, and the coordinator log `evidence/w00/HANDOFF-2026-09-24-weekly-limit.md` (entries "real-8 ROOT CAUSE" and "Rulings: … artifact_missing").

## Scope (product, not harness)

1. When an activation (or any runner operation that needs a release's artifact) hits `artifact_missing`, the host plane rehydrates the artifact into the runner's store from the product's blob copy, verifies the digest named by the release record before use, and retries the operation once. A digest mismatch or a missing blob copy is a named refusal (`artifact_unrecoverable` with {expectedDigest, reason code}); never a silent fallback.
2. Idempotent: a second rehydration of the same release is a no-op; concurrent activations for the same release do not race (join on the release key, as the W4H-26 build operation does).
3. The runner store survives a product restart on the same installation by construction: the store path is part of the installation's durable configuration, not a temp dir; a fresh store on a kept installation is detected and rehydrated lazily.
4. Readiness/diagnostics: the readiness document gains a non-blocking `warnings` entry when a rehydration happened (code, release digest), never a message; the record keeps the count.
5. Contract rows FIRST (C10/C05 amendment: the rehydration operation, its refusal codes, the warning entry), then code. Tests red first for every path: missing artifact → rehydrate → activation succeeds; missing blob copy → `artifact_unrecoverable`; digest mismatch → refusal; concurrent activations → one rehydration; restart on a kept installation → lazy rehydration. 100% of changed lines. A two-boot integration test on a kept store (reuse `tests/store-reuse.test.ts` from W4H-28 as the base; extend, do not duplicate).
6. Mutants the validator will plant: digest check removed; retry loop unbounded; warning dropped; rehydration from an unverified source.

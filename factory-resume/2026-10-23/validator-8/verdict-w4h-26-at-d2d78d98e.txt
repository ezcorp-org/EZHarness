G1 610ca637d renames the supervisor's runner class to escape the Podman-guest guard instead of telling the guard.
- The guard: scripts/podman-guest-job-registration.test.ts:25 STARTS_GUEST = /\bnew \w*PodmanRunner\(|\bextends PodmanRunner\b/,
  "A source that constructs a Podman runner, or defines one". Its intent (header, W4H-12): a CI step that runs a test file
  reaching a Podman guest must run after `bash scripts/setup-extension-runner-ci.sh --install`, or the step fails on
  "image not known".
- The change: src/factory/runner/supervisor-process.ts:309-311 `const { PodmanRunner: HostRunner, ... } = await load();` and
  `return class extends HostRunner {...}`. The class still extends PodmanRunner; only the name the regex sees is gone.
- What the guard said before the rename (run at 2d6fd50ce): "ci.yml factory-deployment-operations (Factory deployment and
  operations): Provision a tenant against the real engine: runs a Podman-guest test before ... --install"
  (the step runs ./tests/postgres/factory-provisioning.test.ts on the factory-real runner).
- Proof that the alias is what silences it: with the alias undone (`PodmanRunner` restored in both lines) the registration
  test is red again (1 fail: "every step that runs a Podman-guest test runs after the runner setup in its job").
- Consequence measured: that suite, run at the head with every podman call logged (a logging wrapper first on PATH), makes 0
  podman calls and 0 guest starts (63 pass). So the guard's flag was a static false positive (the suite reaches
  supervisor-process.ts through imports but never invokes the loader). The class is legitimately host-plane: the supervisor's
  runner for builds and launches.
- Judgment: a rename that escapes the pattern is a gate evasion in form, whatever the runtime truth; the next real
  PodmanRunner subclass written the same way would pass unseen. Acceptable fixes: an explicit, tested exemption in the guard
  that names this loader (supervisor-process.ts / factoryProvisionedRunnerLoader) and its reason (a class definition the
  named suites never instantiate), or a guard rule that tells a defined-but-uninvoked loader apart, with a test; then the
  alias reverted. Re-validation: guard green with `extends PodmanRunner` restored, the exemption's test red when it is
  removed, and my podman-call log of the flagged suite still 0.

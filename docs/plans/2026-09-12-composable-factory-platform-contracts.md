# Factory platform launch contracts

Date: 2026-09-12; amended 2026-09-13. Status: accepted planning decisions; implementation and runtime proof pending.

This is the normative companion to the [platform plan](2026-09-12-composable-factory-platform.md). It resolves the 11 findings in the [initial review](2026-09-12-composable-factory-platform-review.md), the 34 gaps in the [second review](2026-09-12-composable-factory-platform-review-2.md), and the 12 new gaps in the [third review](2026-09-12-composable-factory-platform-review-3.md). Terms are defined in [CONTEXT.md](../../CONTEXT.md); durable tradeoffs are recorded in the [execution-boundary decision](../decisions/2026-09-12-factory-execution-boundaries.md) and the [editor graph-library decision](../decisions/2026-09-12-factory-editor-graph-library.md). Each contract has one proof ID, `F01` through `F13`. A resolved planning finding does not mean its implementation gate has passed.

Where a contract names an existing module, table, or behavior, the statement was verified against main `2588c9f19` on 2026-09-13. An earlier verification read a fix-branch commit 14 commits behind main and was corrected in place. Where a contract names work that the repository does not have, it says so and names the owning stage. C13 is the reuse table for the extension v4 lifecycle that main already ships.

Two terms recur. The host plane is the set of trusted in-installation services: harness, gateway, orchestration process, supervisor. The control plane is only the hosted provisioning service of C12; a self-hosted installation has no control plane.

All limits below are selected product requirements, not measurements. A deployment release lock must contain exact package, container, model-weight, schema, interpreter, and supported runtime/driver versions before execution. Missing lock values block the relevant gate. Do not resolve moving aliases during a run. A required service, credential, or GPU missing from a proof environment is a failed readiness check, not a skipped passing test.

## C01 Tenant and authority

Launch uses one harness installation per tenant in both hosted and self-hosted operation. A tenant contains projects; a user can belong to more than one tenant through separate authenticated sessions. Hosted provisioning creates an installation, isolated product database and database role, storage credentials restricted to its tenant prefix, and an authenticated Temporal namespace. A shared PostgreSQL cluster or Temporal cluster is allowed; sharing tenant database credentials or granting tenants direct cluster access is not. Two components are shared across tenants. The pool admission service in C03 holds capacity reservations keyed by opaque tenant IDs and nothing else. The host supervisor in C05 holds no tenant state and no tenant credentials at all. Neither holds product facts, artifacts, or authority.

The trusted ingress maps a provisioned hostname to a tenant. The server verifies that this tenant matches the installation identity and the session/API-key audience. Never accept a tenant from a body, arbitrary forwarding header, or runner result. Session tokens carry `iss` and `aud` claims equal to the installation ID, and verification rejects a missing or foreign claim. Today's tokens carry neither claim, and verification checks only signature and expiry, so this is new token work in stage 2a. Provisioning (C12) generates a distinct `EZCORP_JWT_SECRET` and `EZCORP_ENCRYPTION_SECRET` for every installation; a shared or templated secret is an F01 failure. The hosted directory contains routing and membership references, not customer artifacts or provider secrets. Instance-global legacy reads remain inside the installation boundary.

Reuse current project membership rows and API-key scope checks, then apply these factory permissions. Three facts about the current code shape that work. Membership is enforced on mutations only, and reads are instance-global by a recorded decision, so membership-scoped factory reads are new enforcement written into every factory route. API-key scope checks apply to keys only; a cookie session is authorized by membership and grants. Scopes have no hierarchy, so each route names its exact scope. `admin` in a tenant installation means tenant administrator, not a global hosted operator. Factory grants are explicit rows in a new `factory_grants` table keyed by tenant, project, principal, and action, with issuer, expiry, and revocation revision. The existing `extension_rbac_grants` and `service_accounts` tables have neither expiry nor a revocation revision and are not reused for factory authority. Owners can grant project actions only within their own scope. Tenant administrators can manage grants; an admin role does not substitute for an exact release approval or trusted acceptance contract.

| Factory action | Required authority | API-key scope / session rule |
| --- | --- | --- |
| List/read definitions, runs, costs, evidence, or live events | Current project member; never a global factory listing | `read` |
| Create/edit/validate a draft or import a definition | Project member plus `factory.author` | `write` |
| Publish a definition version | Project member plus `factory.publish`; an independently approved contract revision | `write` |
| Start a run or request a bounded repair | Project member plus `factory.run`, intersected with the definition and package grants | `chat` |
| Cancel a run | Its current authorized initiator, or project `factory.operate` grant | `chat` |
| Decide an approval or create/revoke automatic release policy | Project `factory.approve` grant; actual human session | `session` |
| Approve an acceptance contract or validator trust | Tenant administrator delegated to that project; actual human session | `session` |
| Request release or reconcile an uncertain receipt | Project `factory.release` or `factory.operate`, respectively; request alone grants no dispatch authority | `chat` / `write` |
| Install/quarantine packages or manage tenant grants | Tenant administrator | `admin`; trust/consent changes remain session-only |

At tenant bootstrap, the first human administrator is the consent authority; provisioning records explicit project consent/trust grants for the bootstrap project and shows them in the audit. Later projects need explicit consent/trust grants too. Creating a new project grants its owner author/publish/run/operate rights, but no automatic release policy. A human can explicitly approve their own draft's protected contract after review; an agent or service principal cannot do so. Record the real human and the exact contract digest. This is human control, not a promise of two-person review.

Service principals reuse the existing service-account identity. Their factory authority comes from `factory_grants` rows with expiry, and stage 2a adds an `expires_at` column to `service_accounts` so a principal itself can expire. They cannot create consent or validator trust. An approved automatic policy can authorize their release requests within its bounds. Removed membership or revoked grants block new dispatches, including dispatch after a long wait. A platform operator has infrastructure access only; product access needs a tenant grant, with an audit record. No implicit operator approval API exists.

Consent, grant, trust, approval, and release facts are product records written in the same transaction as their audit entry through the existing fail-closed helper `insertTransactionalAuditEntry` (`src/db/queries/audit-log.ts`), which aborts the enclosing transaction on failure and already serves v4 releases, runtime locks, and secrets. The ordinary `insertAuditEntry` path is fail-open by design; it receives an informational mirror entry only and is never the record of authority. No third audit path is added.

Every product key and foreign key carries tenant/project scope, even with separate tenant databases. Reject cross-project artifact bindings unless a human has issued a specific read-sharing grant; evidence/release authority does not transfer with read access. Object downloads and subscriptions recheck scope, use opaque references, and do not reveal unauthorized object existence. Byte deduplication must not reveal another tenant's content. Legacy workflow requests are routed only to that tenant's harness, under the initiating/delegated principal and existing workflow grants. Never use a shared global administrator key for the bridge. Reserved legacy project IDs such as `global` or `self` do not bypass factory project grants, and the factory gateway never silently substitutes them for a missing project.

**F01 proof — token rule in stage 2a, tenancy in stage 2d, full in stage 5:** In stage 2a, one test installation configured with two secrets proves that a token signed with the other secret and a token with a missing `aud` both fail. In stage 2d, two real installations created by the C12 provisioner use overlapping project/resource IDs, different membership, human admins, restricted API keys, and service principals; exercise API lists, search, artifact download, provider access, grant and principal expiry, and revocation during a wait. In stage 5, add SSE reconnect, approvals, and the legacy adapter. Foreign sessions, IDs, namespace credentials, and grants must fail at every stage. Audit the allowed path as well as denials, and prove that a failed transactional audit write aborts the product record.

## C02 Worker bridge and operation recovery

The Node.js Temporal worker contains only the trusted kernel and orchestration adapter. It does not import Bun-dependent execution modules or package code. A tenant-scoped execution gateway runs trusted Bun code. The host supervisor on the runner's host launches a fresh isolated Bun or Python runner per active attempt. The gateway holds tenant service credentials; the supervisor holds only its host identity certificate; runners receive only attempt-scoped broker tokens.

**Process topology.** Per tenant installation: the Bun harness and API; one Node.js orchestration process that hosts the Temporal worker for that tenant's namespace and the outbox dispatcher; one Bun execution gateway; and runners launched per attempt. Shared across tenants: the host supervisor daemon on each runner host (C05), which holds no tenant state, and the pool admission service (C03). Only the Node.js orchestration process links any `@temporalio/*` package; the repository has no Node.js runtime process today (Node appears only as the vitest coverage runner and the SDK publish step), and this is the first. The Bun harness, API, and gateway never call Temporal. Product-side requests reach Temporal only through the transactional outbox in the tenant database, which the dispatcher polls. Co-hosting several tenants' workers in one Node process is deferred; it needs per-namespace credentials and a stage 6 capacity case.

**Gateway roles.** The tenant gateway hosts four named roles, each a module of the same process with its own credential set. The provider broker serves model, tool, and guarded network calls for runners and extends the v4 credential and network brokers (`src/extensions/credential-broker.ts`, `network-broker.ts`). The release broker performs publication, is the only holder of publish credentials, and extends the v4 pull-request broker (`src/extensions/project-pull-request-broker.ts`). The fetch proxy serves approved package registries and extends the v4 dependency fetcher (`packages/@ezcorp/extension-runner/src/dependencies.ts`). The archive writer writes the C06 recovery archive. Elsewhere in these contracts, "the tenant's broker" means the provider broker unless publication is meant. Evidence issuer identity lives in the gateway's validator path, never in the supervisor.

**Dispatcher delivery.** The outbox and dispatcher extract the pattern of the v4 `ExtensionDeliveryQueue` (`src/extensions/v4/deliveries.ts`): a deduplication key, a lease with token and deadline, bounded attempts, dead-letter, and an explicit `outcome_unknown` state. They do not add a second queue implementation. A run start uses the workflow ID `{tenant}/{logicalRun}` and a Temporal request ID equal to the command ID, so a repeated start is rejected by Temporal and treated as delivered. Decisions and cross-partition notifications are signals carrying their decision or notification ID; the interpreter inbox in C08 deduplicates them. An outbox row is marked delivered only after Temporal acknowledges. The dispatcher is at-least-once, and every consumer is idempotent by identity. Recovery after a restart follows the v4 `lifecycle-recovery-scheduler.ts`: re-drive every non-terminal operation by identity.

**Interpreter versioning.** Each interpreter compatibility version is a separately versioned worker deployment pinned to a build ID. A run stays on the build ID that started it until it completes, or continues-as-new into a version its snapshot declares compatible. `patched()` markers are not used for interpreter changes. [Worker versioning](https://docs.temporal.io/develop/typescript/workflows/versioning).

Use versioned JSON over private HTTPS with mutual TLS. A certificate identifies the caller service and tenant; the signed attempt token also binds project, run, node instance, candidate generation, attempt, grant revision, resource reservation, deadline, and execution epoch. Certificate/token mismatch fails before work starts. Attempt credentials use exact `tokenUse: "factory-attempt"` claims, separate from login, preview and public service credentials. Their default lifetime is 60 seconds and the installation caps it at one hour; the trusted gateway can mint a fresh credential for an existing attempt. Token expiry is separate from the effect deadline: authenticated status and cancellation remain available after the deadline, while the journal rejects further effects and output advancement. Python and Bun consume the same generated JSON schemas; integer usage counters stay within the shared safe range and monetary amounts use decimal integer strings.

The installation outbox endpoint returns HTTP 200 with a claimed command or JSON `null`; settlement returns 204, and inbox confirmation returns a JSON boolean. Its private HTTP envelope permits 68 KiB so a 64 KiB stored command can carry a lease token and settlement metadata. The C08 encoded Temporal payload limit remains 64 KiB. Definition and transition activity page DTOs use canonical `contentBase64`; their private HTTP page reads return the exact raw immutable bytes, with the original digest and byte count.


| Internal operation | Contract |
| --- | --- |
| `PUT /internal/factory/v1/executions/{attemptId}` | Idempotent submit with canonical request hash; same ID/different hash returns 409; acknowledge only after durable admission record |
| `GET /internal/factory/v1/executions/{attemptId}` | Authenticated status, journal cursor, measured/unknown usage, checkpoint and terminal result reference |
| `POST /internal/factory/v1/executions/{attemptId}/cancel` | Idempotent cancellation request; accepted is distinct from confirmed stopped |
| Result notification | References the recorded result and journal cursor; never accepts authority, evidence issuer, or artifact ownership from callback fields |

The gateway journals every model/tool operation before its possible effect. An operation ID derives from run, node instance, candidate generation, and a monotonically allocated operation index. Retries reuse that operation ID. Commit the exact request and argument digest before dispatch; store the provider receipt/result digest, usage, and resulting workspace snapshot before acknowledging completion. Steps use private copy-on-write workspaces. A completed checkpoint contains the model transcript, operation cursor, tool results, workspace manifest, and all provider/model configurations. Local files and chat logs are not the recovery source.

Operation states are `prepared → dispatched → completed | failed | uncertain`. An expired attempt cannot commit an output or issue another broker request. The gateway verifies the current execution epoch and reservation generation on every effect and final commit. Late results can be retained as reconciliation evidence, but cannot advance the current attempt.

**Native runner extraction** is a stage 2c work item, not an assumption. The existing executor calls providers directly with host-resident keys and persists tool records after completion. The factory runner needs four additions: a pluggable provider transport that sends brokered requests under the attempt token instead of a key; journal hooks before and after every model and tool call; copy-on-write workspace checkpoints; and a runner entrypoint that receives the C02 request. Implement them as options on the shared executor so the chat path and the runner share one code path. A copied executor is rejected in review. Use existing persistence helpers only where their contracts fit. The runner image is built by the v4 recipe machinery (`.runner/recipe.json`: pinned image, SDK, toolchain, seccomp, and limits) extended with the factory's resource classes.

The kernel owns node attempts. Execution activities use Temporal `maximumAttempts: 1`; each product retry creates a new attempt after the prior attempt is confirmed stopped and its uncertain operations are resolved. Workflow-task replay remains Temporal-owned. Transport/control retries reuse the same command/request ID; they never increment the product attempt or start another process. If the Node worker dies but the Bun attempt is still alive, recovery first queries and reattaches to that attempt. A heartbeat timeout alone is not permission to launch another copy.

Pure reads and idempotent broker operations may retry under a node's fixed operation policy. Disable hidden provider-client retries. For a lost model response, retain its worst-case usage reservation; another model request is allowed only if the contract permits repeatable generation and reserves the possible additional charge. A non-idempotent remote effect is reconciled or held for operator review. Runner/package defaults cannot expand retry, token, time, or spend bounds.

Launch defaults: three node attempts including the first; retry delay 1 second then 2 seconds; operation retries at most two including the first; node deadline 30 minutes, bounded by the run deadline. A definition can tighten these limits; widening them requires an approved version and still obeys deployment limits. Agent iterations and repair candidates are separately bounded. Actual policy values are pinned in the compiled definition and shown before a run starts.

The trusted activity/supervisor heartbeat interval is 5 seconds, with a 20-second failure-detection timeout. After cancellation, the supervisor sends an abort, allows 10 seconds for cleanup, then kills the whole sandbox process group. It acknowledges stopped only after the runtime confirms no process remains. Gateway loss revokes broker access; uncertain remote jobs are tracked separately until provider termination/reconciliation. These are target requirements to prove, not guaranteed timing on an arbitrary host. Temporal requires activity cooperation for cancellation; heartbeat delivery and abort signals are documented in [TypeScript activity timeouts](https://docs.temporal.io/develop/typescript/activities/timeouts).

**F02 proof — stage 2c:** Run Node → Bun → real tool and a Python conformance task. Kill Node, gateway, sandbox, and host around each journal boundary; recover on a different host without the prior local directory. Check stable identities, bounded attempts, result reuse, correct workspace bytes, unknown-usage charges, cancellation, and rejection of forged/late callbacks. A surviving original attempt must be reattached or stopped before replacement.

## C03 Admission and reservations

Budget reservations live in the tenant product database. A trusted pool admission service owns compute/provider concurrency reservations in a separate resource ledger.

**Pool admission service.** It is a trusted platform service, one per pool, and it does not exist today. It owns its own PostgreSQL database, separate from every tenant product database. Its rows hold opaque tenant IDs, resource vectors, lease generations, allocation tokens, and queue ages; never product facts, artifacts, credentials, or authority. Tenant gateways authenticate to it with their C02 mutual-TLS certificates, and it accepts a tenant ID only from the certificate. In the self-hosted profile it runs as one process inside the single installation with the same interface. Its ledger is not a source of truth for charges: on ledger loss, every lease is treated as expired, and capacity returns only through the stopping protocol below; budget holds in tenant databases are unaffected. The ledger is included in the C06 checkpoint barrier so a restore cannot double-allocate.

**GPU hosts** are a pool resource class managed by this service. Assignment binds a whole host to one tenant. Release requires a verified reimage receipt from the supervisor before the host is offered again. Hosted operation obtains and returns hosts through the infrastructure provider API; the self-hosted profile uses a static host list. The C11 envelope records GPU host count, assignment latency, and reimage duration.

Acquire the budget first in a transaction that also writes an outbox request for compute. Acquire the complete compute vector atomically in the pool ledger, then return its allocation token. Work starts only after the tenant gateway durably records both reservations and rechecks authority. This is an explicit recoverable sequence, not an assumed transaction across services.

A lost response is looked up by reservation ID. Failure before compute assignment releases the unused budget hold. Orphan compute allocations are reclaimed only by the stopping protocol below. Unique reservation/settlement keys make acquire, cancel, and settlement idempotent. Use canonical lock order for hierarchical budget rows and resource rows. At no point may concurrent children reserve more than the parent's unallocated allowance.

| Reservation state | Allowed action |
| --- | --- |
| `requested` | Wait for budget/capacity or fail by the admission deadline |
| `held` | Capacity assigned, no process acknowledged; confirm start or cancel/reconcile |
| `running` | Renew the lease and account for actual use |
| `revoking` | Reject new effects; stop or reconcile the previous holder |
| `uncertain` | Retain the affected capacity/charge; do not offer it to another holder |
| `settled` | Release confirmed unused capacity and budget exactly once; keep final charges |

Lease rows reuse the shape of `extension_runtime_locks` on main: `fence`, `generation`, an `effects` counter, and states `held | quarantined`. Recovering a lease requires the expected fence and an explicit acknowledgement of uncertain effects, as the v4 `recoverLock` action does today. The allocation generation here is the reservation generation the gateway checks in C02; they are one counter. Each compute lease lasts 30 seconds and renews every 5 seconds. On expiry, increment the allocation generation and deny future broker effects from the old generation. Do not return local CPU/memory/GPU capacity until the trusted supervisor confirms process death or the infrastructure provider confirms the old host is powered off. A network partition cannot prove that. Remote provider concurrency remains occupied until the remote operation finishes or its cancellation is confirmed. Unknown usage never settles as zero.

A subfactory or parent waiting on an approval/child holds no compute slot. Only running leaf tasks consume compute. Parent budget envelopes remain, with portions delegated to child reservations. No task may hold compute while waiting to acquire another compute class; decompose such work into separate tasks. A one-slot parent/child run must progress. New dispatches stop at run cancellation or deadline; settlement and reconciliation continue.

The pool scheduler uses round-robin service across runnable tenants, one feasible allocation per tenant per round for each resource class. Within a tenant, use priority then ready sequence then node identity. After 30 seconds waiting, eligible requests enter an oldest-first lane; hold the next available capacity for an old request until its entire vector fits. Requests larger than the pool's configured maximum fail at admission. A tenant cannot consume another tenant's reserved minimum. No preemption of active work is required. The fairness claim assumes finite task deadlines, functioning capacity, and offered load within the tested envelope.

Bound outstanding admission requests at 10,000 per tenant and 100,000 per pool. Reject new starts with 429 and `Retry-After` when full; never acknowledge work that was not durably queued. Report queue age and its blocking resource. Budget reservation amounts include the maximum charge of every outstanding permitted model attempt; providers without enforceable cost caps produce an explicit estimated-cost contract and a fail-closed unknown-usage hold.

**F03 proof — stage 2d:** Lose each acquire/ack/settlement response, partition a still-running runner, race two children for the last budget unit, cancel during admission, and execute a nested run with one slot. Verify no double settlement, no capacity reuse while the old holder can run, no budget reset, and progress for a small tenant under sustained competing traffic. Assign a GPU host, release it, and prove it is not offered again before a verified reimage receipt; destroy the pool ledger and prove every lease expires and no budget hold changes.

## C04 Acceptance and release dispatch

A trusted human approves the initial acceptance contract revision and validator trust under C01. The generator cannot change that revision. The tenant gateway's validator path constructs evidence from the assigned candidate and validator lock; arbitrary runner JSON cannot mint issuer provenance. The acceptance service verifies every mandatory claim, artifact digest, environment/configuration digest, execution identity, issuer grant, and evidence freshness. It writes an immutable decision bound to the exact candidate, contract, and evidence set.

`ReleaseOperation` has a stable tenant/project ID, run/node link, candidate digest, acceptance decision, action, destination account and object identity, expected destination version if relevant, canonical request hash, and policy revision. The database enforces one operation per run/release-node/candidate/action/destination. HTTP idempotency keys follow the v4 convention (a bounded key plus input digest) and are scoped to tenant/project/principal/verb/resource; reusing a key with different bytes returns 409. Keep operation identity and consumed-approval records for as long as the release audit is retained. Never treat HTTP key expiry as permission to repeat a release.

Approvals, policies, and release operations are factory tables that reuse the v4 lifecycle's code and shape rather than a parallel design. `LifecycleApproval` (`src/extensions/v4/lifecycle.ts`) is durable, human-only, single-use, bound to a release digest, an exact grant list, and an expected generation, and re-validated at every use. `extension_project_decisions` and the pull-request broker (`src/extensions/project-pull-request-broker.ts`) implement the digest-bound proposal, the 24-hour window, the atomic single-use claim, and the never-retried uncertain outcome. Extract the approval check, the claim compare-and-swap, and the uncertain-outcome settlement into shared modules used by both v4 and the factory, and add tenant, destination, policy revision, and reconciliation fields for the factory. What v4 lacks and this contract adds: automatic release policies, the three reconciliation actions below, the recovery archive, and tenant scope. Contract-digest re-consent follows the delegation consent-hash and widening-only reconcile pattern in `src/runtime/workflow-capability-hash.ts` and `src/runtime/workflow-consent-reconcile.ts`. The legacy `workflow_approvals` table and the process-local tool gates are not reused.

A human approval binds one operation ID and expires after at most 24 hours; it is single-use. Reusable automatic authority is a separate policy with explicit project, principal, action, destination prefix/repository, acceptance contract, maximum operations and spend, and expiry of at most 30 days. Counters are consumed atomically at dispatch, not at request creation. A new run wanting the same content at the same target must receive its own authority; adapters must still avoid duplicate publication where the destination contract forbids it.

Dispatch follows this order:

1. Persist the operation and pinned candidate/evidence references. Store an immutable recovery intent in the independent release archive described in C06; verify that it is readable. If either store is unavailable, wait without dispatch.
2. In one product transaction, lock the operation, run cancellation epoch, applicable policy/grants, and approval/counter rows. Check acceptance/freshness, current membership, package/validator trust, deadline, archive receipt, and current release-enable epoch. Check any adapter reservation on the destination. Atomically consume the exact approval or policy allowance and claim `pending → executing` with a dispatch generation. Only one claimant wins.
3. This committed claim is the authorization point. Revocation or cancellation committed before it prevents dispatch. After it, the operation is in flight; revoke future work and attempt cancellation, but do not promise to undo a remote write. Send only the exact request under the claimed generation.
4. The broker uses provider idempotency/conditional writes or the adapter's serialized reconciliation protocol. Persist the confirmed provider receipt in the recovery archive, then the product database. Notify orchestration through the outbox. Late receipts may settle the same operation but cannot authorize a different one.
5. A lost response becomes `uncertain`. Before a new dispatch, fence the old sender and establish the provider outcome. If no reliable absence proof exists, keep it uncertain and require operator evidence; do not retry because a timeout elapsed.

Reconciliation actions are `attach verified receipt`, `confirm failed/no effect`, and `keep uncertain`. Each needs a scoped operator, reason, and provider evidence. Confirmed absence plus a stopped old sender permits an explicit new dispatch claim that rechecks current authority. A failed/uncertain original dispatch consumes its single-use approval; another potentially effective send needs new consent or unused automatic policy allowance. Receipt lookup and settling an already completed send need no new release consent. Compensation is a separate accepted and authorized operation.

The release broker, the gateway role defined in C02, is the only holder of publish credentials. Candidate runners cannot reach arbitrary network destinations, shared publish directories, Git remotes, or object-store write APIs. General tool grants authorize private workspace operations and brokered generation, never publication. This rule also applies to speculative join branches and legacy adapters exposed as factory tasks: publication-capable legacy steps are rejected unless their effects are mediated by the release broker. Existing workflows outside factories retain their behavior.

**F04 proof — core in stage 3 with fixture adapters, real-adapter legs in stage 5:** Race dispatchers, policy revocation, cancellation, approval expiry/reuse, changed request bytes, and destination version changes on both sides of the claim. Prove an approval request produces one delivery in the C11 notification outbox. In stage 5, with the real GitHub and S3 adapters and the legacy adapter: drop the provider response after a real write, stop the old sender and reconcile without creating a second effect, and try to publish through an ordinary agent/legacy tool. An unresolved receipt must remain visible and must not become success when the run ends.

## C05 Package lifecycle and isolation

The supported CPU profile is the rootless Podman profile that main already ships and probe-enforces in `packages/@ezcorp/extension-runner/src/podman.ts`: cgroups v2 with memory, CPU, and PID controllers; a deny-by-default seccomp profile; `--network=none`, `--read-only`, `--cap-drop=ALL`, no-new-privileges, a non-root UID, private PID/IPC/cgroup namespaces, no host sockets, a `noexec` tmpfs, an environment of exactly `HOME`, `TMPDIR`, and `BUN_INSTALL_CACHE_DIR`, and a live probe that refuses to run unless the kernel reports every control. Factory runners add an attempt-private writable workspace, host-enforced egress to the tenant provider broker only (the v4 runner has no network; the factory runner's only route is the broker), and the C03 resource classes. The earlier selection of gVisor `runsc` for this profile is withdrawn: it would have replaced a shipped, probe-enforced runtime with a second one. The [execution-boundary decision](../decisions/2026-09-12-factory-execution-boundaries.md) records the change. Verify applied configuration from the supervisor and the runtime API, not sandbox-supplied output.

The GPU profile uses the same Podman runtime with Container Device Interface (CDI) injection of one whole GPU on a tenant-dedicated GPU VM/host, the same seccomp profile and probe, and an explicitly supported NVIDIA driver/toolkit pair. Do not colocate host-plane services or another tenant on that host. GPU capacity is never shared across attempts. Limit driver capabilities to compute/utility; reset the device before reuse and reimage the host before tenant reassignment. Driver compromise remains part of the GPU threat model; patching and a dedicated host are required. Unsupported driver pairs fail readiness. GPU host assignment and reimage are pool operations under C03. If F05 shows that Podman device injection cannot meet the isolation gate, gVisor `nvproxy` is the recorded alternative for the GPU profile only. [gVisor GPU compatibility and security](https://gvisor.dev/docs/user_guide/gpu/).

Nothing in the repository configures a GPU today; the GPU profile is new. The image ships two isolation stacks: the bwrap/netns/nftables stack with a setuid-root preview helper for MCP servers, and the rootless-Podman v4 runner for extensions. Both stay as they are for the harness container.

**Degraded tier.** v4 permits a `TrustedLocalRunner` only under a digest-bound admin waiver that lists every omitted control and is audited on each use. Factory runners have no degraded tier at launch: an unavailable isolation control fails admission.

**Host supervisor placement.** The supervisor runs outside every sandbox as a host-level daemon: a systemd unit or privileged Compose service in the self-hosted profile, and a privileged DaemonSet in Kubernetes. It is the only factory component with container-runtime access. It holds only its host identity certificate: no tenant credentials, no attempt tokens, no evidence issuer identity; those stay in the tenant gateway. Factory runners are launched by the supervisor, never from inside the harness container, so the harness container keeps its current runtime and MCP launcher unchanged. The runner image contains no setuid helper. Changing the harness container's own runtime is deferred.

**Base hardening (stage 2a).** Verified against main. Two items are closed and keep regression tests; three are open and block F05:

1. Manifest loading — closed on main. The extension installer and loader throw `EXTENSION_V4_REQUIRED`; the source digest is verified before any code runs, and the manifest is discovered by an RPC inside the container whose reverse-RPC handler denies every host capability (`podman.ts`). F05 keeps a regression test.
2. Reserved paths — open, every installation. The deny set covers `.ezcorp/data`, `.ezcorp/backups`, and the PGlite mask directories, which are empty on external PostgreSQL; the master key file then lands in the process working directory inside a `$CWD` grant (`src/providers/encryption.ts`, `src/extensions/permissions.ts`). Add the secrets directory, `.pi-secret`, `.pi-salt`, and `.env` to the deny set for every installation, and require `EZCORP_SECRETS_DIR` outside every grantable root in factory-enabled deployments.
3. Fail-closed seams — open, factory-enabled deployments. Extension code no longer spawns host subprocesses on main (`release-process.ts` throws). ## C06 Durable records, retention, and restore

Temporal remains authoritative for execution decisions. Product facts have their own durable IDs in PostgreSQL. A trusted orchestration activity appends a canonical audit batch before completing each externally visible kernel transition. Its stable producer key is `(tenant, logicalRun, interpreterId, sourceSequence)` with a batch digest and predecessor digest for that interpreter stream; `interpreterId` is the Temporal workflow ID of the interpreter partition and `sourceSequence` is that interpreter's monotonically increasing transition counter. The append uses the existing fail-closed helper `insertTransactionalAuditEntry`. A unique constraint deduplicates this key. The append transaction allocates the next logical-run projection sequence under a run-row lock, so concurrent partitions share an ordered feed without guessing each other's sequence. A retry returns the originally assigned projection sequence. Same producer key/same digest is a no-op; a changed digest fails. Append before issuing the transition's effect commands. Replay retries the append by the same key. The audit stream records proposed command identities, completion/failure outcomes, selected branches, attempts, usage, and terminal state; it does not independently schedule work.

Consumers update a run projection and cursor in one transaction. Apply only the next contiguous sequence, ignore verified duplicates, and stop on gaps/conflicting digests. A snapshot contains a verified sequence and digest; rebuild replays subsequent batches. Product approvals, evidence, release receipts, and grants remain immutable facts or revisioned policy records, not projections. The product stream can lag Temporal; that lag must be visible, and projections cannot grant authority.

Keep active run records, dependencies, interpreter/worker versions, journals, artifact content, and decryption keys until no active reference needs them. Default retention after completion is 30 days for ordinary Temporal history, 90 days for unaccepted candidates/debug logs, and 365 days for the canonical run audit, accepted evidence/artifacts, approvals, release identities, and receipts. A release can extend retention; it cannot shorten it below the advertised audit period. Deletion first tombstones the product object and stops new work. It never cascades away receipts or active references. GC checks authoritative references, verified archive copies, and retention deadlines. Tenants can explicitly request final purge through the C09 purge surface after active work and unresolved operations are closed; record what audit is lost and require a human administrator.

Archive canonical audit batches and referenced snapshots before allowing their primary records to expire. Archival failure stops cleanup. Configure Temporal history archival for diagnostic replay during the product audit period; it does not become a second live execution engine. Encrypted payload codecs and key version retention apply to history, archives, snapshots, and backups. Store credential handles, not raw provider tokens, in history or audit.

**Key hierarchy.** Each installation has a data key that encrypts payload codecs, archives, snapshots, and backups. Hosted operation wraps the data key with a cloud KMS key; the self-hosted profile wraps it with an operator-supplied master key stored outside every grantable root, or with an external KMS. The wrapped data-key file is a separate Node orchestration-process secret; the Node process receives that file and its master-key file, never database, S3, provider, or raw data-key credentials. Rotation re-wraps the data key and retains prior key versions for the audit period; it never re-encrypts stored objects in place. The current master key is a file generated on first boot with no rotation surface; factory-enabled deployments require the explicit key and fail readiness without it.

**Object storage prerequisites.** No S3 client or configuration exists in the repository, but a content-addressed `BlobStore` interface with a digest-verifying local implementation does (`src/extensions/v4/types.ts`, `src/extensions/v4/blobs.ts`). Stage 2b adds an S3 implementation of that interface with conditional create, version reads, checksum verification, multipart upload, and prefix-scoped credentials; every store passes the object-store conformance suite, run in the `Factory Temporal integration` lane, before use. The MinIO AIStor Free license and configuration are a deployment-operator prerequisite named in the C12 installation checklist and verified by readiness.

The independent release archive uses conditional-create immutable objects under a tenant/release-operation prefix. It has separate credentials and an independently replicated failure domain, beyond the databases and ordinary backup restore. It stores the full release request, operation identity, referenced acceptance/evidence manifests, dispatch/receipt facts, and archive checksums without publish secrets. Normal product and restore credentials cannot delete or overwrite it. Dispatch waits until every referenced object needed for reconciliation is durably available there. Restoring an old database must not restore or erase this archive.

Use continuous PostgreSQL WAL backup and versioned object storage. The backup coordinator establishes a compatible checkpoint across the product and Temporal stores: stop new mutations/effect claims, drain or fence active effect senders, wait for all accepted outbox/audit writes to be reconciled, record each run's execution chain and product/audit cursors, stop workflow-worker dispatch, and take both database recovery positions plus object version manifests. Waiting approvals/children may remain, but their entire run trees must be included and no product-affecting command may cross the barrier. Temporal timer delivery while workers are stopped is harmless recorded work for recovery. Resume only after the checkpoint manifest is sealed in the independent archive. If the barrier cannot complete, no compatible checkpoint is claimed.

The barrier is per tenant installation. It stops that tenant's dispatch and effect claims, drains its senders, and records that tenant's product database position, the pool ledger rows for that tenant, and object version manifests, while that tenant's namespace is quiescent. Temporal persistence is a shared, independently highly available store and is never restored per tenant; a tenant restore reconciles the tenant's records against the live namespace. A Temporal-cluster restore is a cluster-wide disaster: every tenant on that cluster enters the restore epoch together, and the Temporal position the barrier also records is used only in that case. Barriers run concurrently across tenants with at most 16 in flight; with 100 tenants, a 10-second maximum, and 16-way concurrency the worst case is about 70 seconds per cycle, inside the 15-minute bound. The target barrier duration is 2 seconds and the maximum is 10 seconds; past the maximum the barrier aborts without claiming a checkpoint and the next attempt is scheduled. Barrier windows are excluded from C11 steady-state percentiles, like fault windows, and are counted toward availability and reported with their count and duration.

Produce a compatible checkpoint at least every 15 minutes and retain continuous recovery data between checkpoints. Alert and stop new external effect claims when the newest verified checkpoint is older than this bound. This trades availability for a provable recovery bound. Stage 6 must measure that this procedure is viable at the launch load. An online replacement protocol must prove the same consistent-cut property before replacing the barrier.

For ordinary process/node/network failures, lose no acknowledged durable fact. For loss of the primary database failure domain, the launch disaster target is at most 15 minutes of uncheckpointed internal progress and recovery within 4 hours after replacement infrastructure and archive access are available. No previously dispatched release identity may be lost while the independent release archive survives. Simultaneous loss of primary data and the independent archive is outside this recovery guarantee; fail closed instead of claiming safe automatic reconstruction.

Restore into a new execution epoch with all admissions and release claims disabled. Verify backups, keys, object manifests, cursors, and compatible database recovery positions. Fence the old deployment at ingress, credentials, brokers, and infrastructure; stale workers must not dispatch. Rebuild projections, import missing product release facts from the surviving archive, and reconcile every post-checkpoint release and uncertain operation with its provider. Resume existing Temporal histories only from restored Temporal persistence; do not invent histories or start duplicate replacement runs. If no compatible checkpoint or required receipt can be established, keep affected runs/releases blocked and expose the reason. Enable service only after an operator signs the recovery report under tenant authority.

**F06 proof — storage in stage 2b, full restore in stage 6:** Expire ordinary history and delete only test projections; reconstruct the full promised run view from the canonical archive. Inject sequence gaps, duplicate/conflicting batches, missing object versions, and lost keys. Restore mismatched database backups after a real release and prove the service stays closed. Restore the latest compatible checkpoint, fence surviving old workers, recover all release identities/receipts, and measure internal data loss and recovery duration against the declared targets.

## C07 IR values and control semantics

`@ezcorp/factory-sdk` owns the only execution schema and its versioned JSON Schema export. The compiler, Bun/Node boundaries, Python runner contract, editor, and simulator consume it. Code generators may produce language bindings; handwritten alternative execution schemas are forbidden. A version consists of definition content, acceptance contract, dependency lock, and interpreter compatibility version. Runtime grants and human approvals are separate product facts; a definition cannot grant itself permission.

**Identities and counters.** These terms are used across the contracts and are defined here once.

| Term | Definition | Owner |
| --- | --- | --- |
| Logical run | The stable identity of one factory run across every Temporal execution, partition, and continuation | Kernel; product tables |
| Interpreter | One Temporal workflow execution that hosts the kernel for one partition of a logical run | Temporal adapter |
| Partition | A compiler-assigned subset of node instances executed by one interpreter (C08) | Compiler |
| Candidate generation | A per-node-instance counter that increments on repair or replan; part of every operation ID and attempt token; carried in the continuation snapshot | Kernel |
| Attempt | A per-candidate-generation counter that increments on retry (C02) | Kernel |
| Allocation generation | A per-lease counter in the pool ledger that increments on lease expiry; the gateway checks it as the reservation generation (C03) | Pool admission service |
| Dispatch generation | A per-release-operation counter assigned at the dispatch claim (C04) | Release broker |
| Cancellation epoch | A per-run counter that increments on cancellation or deadline expiry | Kernel |
| Execution epoch | A per-installation counter that increments on a C06 restore; every attempt token carries it, and the gateway rejects tokens from an older epoch | Restore procedure |
| Release-enable epoch | A per-installation counter that a restore or an operator increments to re-enable dispatch after a hold (C04, C06) | Operator |

The launch value format is I-JSON. Reject duplicate JSON/YAML keys, YAML executable/custom tags or aliases, non-finite numbers, unsafe integer values, and unpaired Unicode surrogates. Treat missing and null as distinct. Use own-property access, never prototype traversal. Encode currency/large integer data as decimal strings or typed artifact contents. Hash canonical execution JSON with SHA-256 under RFC 8785; presentation metadata has a separate digest. Array order is significant. Resolve dependency references and materialize defaults before hashing. Equivalent supported authoring inputs produce the same canonical IR. [JSON canonicalization](https://www.rfc-editor.org/rfc/rfc8785).

Supported port schema keywords are `type`, `properties`, `required`, `additionalProperties` (boolean), `items` (one schema), `minItems`, `maxItems`, `minLength`, `maxLength`, `minimum`, `maximum`, `enum`, `const`, `$defs`, and local `$ref`. Types are object, array, string, number, integer, boolean, null; a nullable union may contain one type plus null. References must be local and acyclic. Descriptive title/description fields do not affect compatibility. Reject remote references, recursive schemas, regex/pattern validation, combinators, executable formats, defaults with side effects, and every unknown execution keyword.

Compatibility uses conservative structural containment: producer type must fit consumer type, each consumer-required property must be guaranteed by the producer, nested shapes must fit recursively, producer ranges/enum values must be subsets, and extra properties must be permitted. Integer is a subset of number; missing is not null. If containment cannot be proved, reject the binding or require a declared conversion node. Conversion output still undergoes runtime validation. Validate external run input before start, node input before dispatch, node result before success, and subfactory outputs before parent use. Artifact references are host-issued records with verified tenant, project/read-sharing grant, content digest, size, media type, and storage version. Recheck bytes when consuming a blob; a client-supplied hash alone is not evidence.

**Validation placement.** Inline values are validated inside the workflow by the SDK's generated validator, which must be free of code generation and deterministic: no `new Function`, no regex, no network, no ambient time. F07 proves the validator runs under the Temporal workflow bundler. Referenced artifacts, pages, and collections are validated in recorded activities. The same generated validator runs in Bun, and its generated equivalent runs in Python; a validator that works in only one runtime is rejected.

Expressions are bounded AST data: `literal`, `ref`, `exists`, `eq`, `lt`, `lte`, `gt`, `gte`, `not`, `and`, `or`, `in`, and `length`. References select only named inputs, declared ancestor outputs, map item/index, or loop carried/result values with typed path segments. `eq` compares canonical JSON; ordered comparison accepts two numbers or two strings of the same type; boolean operators require booleans and short-circuit left to right. Missing references are errors except under `exists`; `length` accepts strings/arrays. No implicit coercion, arithmetic, network, ambient time, arbitrary code, or mutable state is available. Each expression is at most 256 AST nodes, depth 16, and 1,024 evaluated steps; exhaustion is an execution failure, never a false/pass result.

There is no arithmetic. A loop's `until` and `nextInput` select and compare recorded values only; any derived value between iterations is produced by a task node. The kernel owns the iteration index and exposes it as a read-only reference. Branch is binary; a multi-way selection composes nested Branch nodes, or a task returns an enum that `eq` consumes. A reducer is an ordinary Task node declared over a Map `collect` result; the kernel has no other merge.

| Construct | Exact launch behavior |
| --- | --- |
| Task | Emits one logical dispatch identity; attempts follow C02; schema-invalid output is `OUTPUT_INVALID`, never success |
| Branch | Evaluates one boolean predicate over recorded input; selects `then` or `else`; predicate errors fail the branch; inactive paths are skipped |
| All join | Waits for every selected required predecessor; an unhandled failed required input fails the join; zero selected inputs succeeds with an empty result |
| Any/quorum join | Requires explicit eligible terminal outcomes and a positive quorum; commits the first qualifying recorded input set, ordered by event sequence then node ID; zero eligible inputs or insufficient remaining candidates fails |
| Map | Snapshots an ordered input collection; items are distinct by index; `all` mode fails on an unhandled item failure; `collect` mode returns ordered typed per-item outcomes; empty input returns an empty collection |
| Loop | Executes its child at least once; initial carried input is explicit; after a successful child, evaluates `until` against that iteration's result; true returns that result, false evaluates typed `nextInput` for a new iteration; false at a bound fails or emits a configured escalation wait |
| Subfactory | Uses the pinned child and intersected authority; validates input/output at both boundaries; never allocates a parent compute slot while waiting |
| Approval | Creates one durable approval request with explicit choices, context digest, authorized actor scope, and absolute expiry; one decision wins; expiry/denial follows a declared failure or escalation path and never implies consent |
| Acceptance | Applies the protected C04 contract to an exact candidate and evidence set; a rejected candidate can enter a declared bounded repair loop |
| Release | Calls C04 for an already accepted candidate; terminal graph completion cannot overwrite an uncertain release state |

Branch structure must have explicit entry/merge scopes; the compiler rejects bindings from an inactive branch unless the receiving schema is optional and a merge supplies that meaning. Quorum results contain winning node IDs and outputs, never arbitrary last-writer merging. Losing work receives cancellation; shared descendants still required by a selected path are not cancelled. Speculative branches cannot contain a Release node or an effect that requires publication authority before their winning selection. Cancelling a speculative branch cancels its pending approval requests; a decision that arrives after cancellation is recorded as late and ignored, and a single-use approval already consumed inside a losing branch is spent. A valid quorum can succeed despite losing candidate failures; required errors outside declared outcome-collection/join scopes fail the enclosing graph.

Default graph failure is fail-fast at the enclosing scope: block new ordinary work, cancel active descendants, retain outcomes/charges, and enter `stopping`. Map `collect` and explicitly declared qualifying join outcomes are the only launch failure-containment forms. Cleanup/reconciliation commands remain allowed while stopping. Successful early joins may advance selected downstream work while losers stop, but the run is not terminal until every started child/attempt is stopped or has a durable uncertain-operation record and a revoked execution token. Local unconfirmed running work keeps the run in `stopping` and raises an alert.

Every run has an absolute deadline: seven days by default, at most 30 days at launch. A definition may tighten it. A node deadline is 30 minutes by default and at most 24 hours at launch; a definition may tighten it and may widen it only up to that maximum. Approval nodes can wait at most 24 hours per request; an escalation does not reset the run deadline or automatically create another consent request.

Run execution states are `created`, `running`, `waiting`, `stopping`, `completed`, `failed`, and `cancelled`. Waiting has a reason (approval, admission, remediation, or external reconciliation) and an absolute deadline. Completed requires all required graph outputs and no unresolved required Release node. Failed/cancelled can retain separately visible uncertain external operations. Node states are `blocked`, `ready`, `reserved`, `running`, `waiting`, `retry_wait`, `stopping`, `succeeded`, `failed`, `skipped`, and `cancelled`. Acceptance and release keep their own records; no combined mega-status exists.

Cancellation or deadline expiry increments a run cancellation epoch and wins over later dispatch claims. Apply events in their recorded order. A completion already committed before cancellation remains in history; a later completion cannot revive cancelled work. Loop elapsed time, budget, and run deadlines span retries and continuations. Replan creates a validated child revision and stops the replaced active scope before starting it. A broader contract/grant needs human authorization and a new run/version. Completed evidence never changes ownership to a repaired candidate.

**F07 proof — stage 1, in-bundle validator in stage 2b, Python equivalence and boundary checks in stage 2c:** Golden schema fixtures and event traces cover every table row, loop carried values and exit/exhaustion, zero-input joins/maps, skipped optional inputs, contained versus unhandled errors, retry exhaustion, early winners, stale events, cancellation, malformed outputs, and artifact ownership/hash mismatch. Replay/property tests must compare expected states and command identities, not only two executions of the same implementation. In stage 1, reject unsupported JSON Schema/AST forms consistently in every authoring path and prove by static check that the generated validator contains no code generation. In stage 2b, execute the generated validator inside a Temporal workflow bundle in the time-skipping test environment. In stage 2c, prove the Python validator rejects the same forms.

## C08 Payloads, partitions, and continuation

These product limits apply to both launch deployment profiles and are lower than the underlying Temporal hard limits. Temporal Cloud documents separate request and history-transaction limits, so event-count limits alone are insufficient. [Temporal limits](https://docs.temporal.io/cloud/limits).

| Limit | Launch value |
| --- | --- |
| Expanded node instances per logical run, including loop/repair/replan instances | 10,000 |
| Subfactory/graph scope depth | 16 |
| Full compiled definition and lock in object storage | 16 MiB |
| Encoded Temporal activity/signal/update argument or result | 64 KiB |
| Aggregate encoded commands emitted in one workflow task | 512 KiB |
| Recorded plan/data page loaded by an activity | 32 KiB |
| Inline run/worker public input | 64 KiB; larger values use validated artifact/collection references |
| Node instances in one execution partition | 128, further split if its bytes/event budget requires it |
| Simultaneous activities per interpreter workflow | 32 |
| Simultaneous child workflows per interpreter workflow | 32 |
| Planned history budget per workflow run | 8,000 events or 8 MiB, whichever comes first |
| Stop new work and start drain/continuation | 4,000 events or 4 MiB |
| Live/continuation control snapshot | 64 KiB; large completed maps/history use immutable manifest references |
| Queued distinct control decisions per logical run | 128; redundant decisions deduplicated in the inbox |

The compiler builds immutable partition/page manifests. A workflow receives a manifest reference and its digest, then loads required bounded pages through recorded activities. It never performs an unrecorded object-store read. Do not return the full IR as one activity result. Results, errors, logs, map inputs, and reductions all obey payload bounds; use manifests plus ordered page references for large collections. A 10,000-item map is not an array of 10,000 full results in the parent history or browser.

Partition by execution/history needs, not visual nesting. Within a partition, ready successors still progress independently. Compile a topologically ordered partition dependency graph so partitioning cannot introduce a dependency cycle. Cross-partition dependencies use durable per-node completion notifications addressed to the successor interpreter through the dispatcher (C02). Emit a notification as soon as its node completes, not when its whole partition/child finishes. The root tracks partition lifecycle/admission and final manifests; it does not receive every node event. Store notifications for a not-yet-started partition until it is admitted. Thus unrelated slow nodes are not implicit dependency barriers; explicit interpreter/pool capacity may still delay admission. Admit tasks in windows, but retire completed partitions independently. Bound concurrency for every workflow in the hierarchy, not just the root.

Before scheduling a task, reserve history space for its complete worst-case command/event path, including failure, result pages, cancellation, and at most the pinned number of attempts. Transport retries and status heartbeats do not emit unbounded workflow signals. If the remaining history cannot cover already admitted work plus a checkpoint/close, stop admitting new work early. Fault tests must validate this accounting against the pinned Temporal SDK/server; a budget estimate is not proof.

Continue-as-new only with no active execution activity or child workflow in that interpreter. Stop admitting new children and let existing children drain; an approval wait produces no polling loop or unbounded events. If a child must outlive the parent's budget, compilation must place that wait in a partition whose parent reserves enough close/result space, rather than rely on an undocumented handoff. No active child is abandoned to cross a continuation boundary. Temporal explicitly does not carry ongoing children into a continued parent. [Child-workflow continuation](https://docs.temporal.io/child-workflows).

An approval is a product fact addressed to the stable logical run and approval ID, not a Temporal Run ID. The transactional inbox stores a unique decision and outbox delivery. A trusted dispatcher resolves the current workflow execution chain. During continuation it retains the command until the successor acknowledges it; retries keep the same decision ID. Inbox limits, membership checks, and single-use decisions prevent event flooding while a run waits.

The continuation snapshot carries schema/interpreter version, tenant/project/logical run identity, definition/partition manifests, current scope, live dependency counters, branch/join winners, candidate generations and attempt counters per node instance, loop counters and carried references, completed-output manifest, logical command counters, last applied interpreter-inbox sequence, unresolved approval IDs with absolute deadlines, budget/reservation references, and cancellation/execution epochs. Drain running activities/children first; move completed data to manifests if needed. Re-create timers from absolute deadlines; never reset elapsed-time limits. Persist acknowledged inbox positions across the entire execution chain; retain ID/hash tombstones in the product inbox for the run's audit period. Old/out-of-order callbacks are checked against their command, attempt generation, and applied sequence and cannot become new work.

**F08 proof — stage 2b:** Load a 10,000-node graph with maximum supported metadata, paged map inputs/results, bounded retries, and nested scopes. Force repeated continuation below server limits. Deliver an approval/cancel before, during, and after continuation and replay the full chain. Check encoded payloads, pending-operation counts, history budgets, immutable data refs, branch readiness across partitions, and that no child is orphaned. Oversize definitions/values must fail with a located error before external work.

## C09 API, authoring, and console behavior

Factory API resources live under `/api/factories`. Use one validated request/response schema source from the SDK. Register every route and its actual scope in `src/api-registry.ts`; generate client/OpenAPI definitions from the existing registry path. Register event names in the existing canonical runtime event-name module. `web/src/__tests__/route-contract.test.ts` (registry parity, declared scopes, and event names) and `src/__tests__/session-scope-surface.test.ts` enforce all three; a scopeless entry or an unregistered route fails them. Main already gates every route that activates code behind a human session with a 202 and a queued operation; factory routes follow that posture.

The console is a first-party SvelteKit route family under `/factories`, not an extension Hub page; the Hub schema renders nine fixed node types and cannot host it. The browser route-coverage manifest fails closed on any scripted route absent from a lane, so a `/factories` route file and its lane entry land in the same change. Factory identifiers are `factories` and `factory-*` in routes, specs, coverage keys, and branch names; `ez-factory` names only the existing bundled extension. Definitions expose `availability: available | unavailable` with a reason derived from their required resource classes; the console shows it, and a CPU-only installation shows the image reference factory as unavailable. The editor uses Svelte Flow and ELK under the [editor graph-library decision](../decisions/2026-09-12-factory-editor-graph-library.md). A boundary test forbids importing either library outside `web/src/lib/factory/`; wrapper components are covered at 100% like any new file.

**Feature flag.** The flag is `EZCORP_FACTORY_ENABLED=1`, read once at boot; any other value or absence is off. No feature-flag system exists today, and the one settings-row toggle in the codebase is deliberately fail-open; the factory flag is an environment value and fails closed. When on, these are readiness requirements and this is the single list of required factory services: Temporal, external PostgreSQL, object storage, the Node.js orchestration process, the execution gateway, the host supervisor, the pool admission service, and the required-sandbox setting in C05. An embedded-PGlite installation with the flag on fails startup with a named error. When off, no factory service starts, factory routes return 404 with a `factory-disabled` reason, and legacy routes are unchanged.

**Migrations.** Factory DDL is idempotent and additive, runs through the existing migration mechanism on every installation regardless of the flag, and gates only services. External PostgreSQL has no snapshot, rollback, or circuit breaker today; those exist on the PGlite path only. A factory rollback is therefore a code rollback over additive schema, and no migration may depend on a later code version to be safe. Test a clean installation, a current-main upgrade, and rerunning migration on external PostgreSQL. F09 measures the added boot time of the factory DDL on PGlite and PostgreSQL and reports it.

| Run start, status, cancel, repair/replan request | Pin input/definition/grants; return logical run and command IDs; do not turn a request acknowledgement into a completed state |

### Reference code factory v1

Definition ID `reference.code.v1`. Input: tenant project repository connection, immutable base commit SHA, issue/request text, destination repository, and base branch name. Supported launch repository: a Bun/TypeScript package with a checked-in frozen lockfile and explicit build/typecheck/test scripts. Native harness agent generation uses the Anthropic provider with `claude-haiku-4-5-20251001`; maximum 12 agent iterations and three candidate generations including the first. Provider requests/results are journaled under C02. The current provider documentation lists this model ID and image/text input support. [Claude model reference](https://platform.claude.com/docs/en/models/overview).

Graph: snapshot repository → generate private candidate → freeze complete Git tree/commit → protected checks → acceptance → on rejection, bounded repair to a new candidate → exact approval/automatic policy → GitHub PR release. A candidate commit must have the pinned base commit as its parent and include the whole resulting tree. No submodules, Git LFS pointers, symlinks escaping the candidate tree, or repository-controlled network installs are supported in this reference version.

Protected mandatory claims: frozen dependency installation succeeds; build, typecheck, and the declared test suite exit zero; the fixture-specific protected tests pass; no high/critical dependency finding in the pinned advisory snapshot; no secret-scanner finding; changes stay inside the request's allowed paths; protected test/config files remain unchanged; and an independently supervised review evaluator reports all rubric fields true (`matchesRequest`, `noUnrequestedEffect`, `noKnownCriticalIssue`). Reviewer errors/missing fields are not passes. The review model uses the same explicit model ID in a separate validator context without tool/publish grants; its decision is probabilistic evidence, not independent calibrated certainty. Validation operates on a writable disposable copy whose input tree digest is verified; the canonical candidate and protected assets remain read-only.

Golden valid fixture: `slugify("Hello, Factory!")` returns `hello-factory`, with protected tests for empty input, punctuation-only input, and repeated spaces. Bad fixtures return `Hello-Factory!`, remove the protected test, or write outside the allowlisted source file. Repair must produce a new tree and rerun all mandatory claims. Default claim freshness at release is 24 hours for deterministic checks and 15 minutes for the advisory/review evidence; the contract can tighten these values.

GitHub release extends the v4 pull-request broker (`src/extensions/project-pull-request-broker.ts`): its digest-bound proposal, human decision, atomic claim, host-held token, and never-retried uncertain outcome are reused, and the factory adds the branch namespace, the tested-base binding, and the receipt fields below. It uses a tenant GitHub App restricted to the selected repository. It creates a unique immutable branch `factory-release/<operationId>` at the accepted commit and opens one draft PR to the named base branch. Configure that branch namespace so only the release broker can create/update its refs; verify this during adapter setup in stage 5, and F10 checks it. Never force-update a conflicting ref. Bind the approved request to repository ID, accepted SHA, tested base SHA, base branch, title/body digest, and branch name. The PR body identifies the exact tested base; opening a PR does not claim the current moving base or merged tree was tested. Merging is outside this adapter's action.

Reconcile a lost branch-create response by reading that exact ref and comparing the SHA. PR creation has no assumed idempotency key: lookup all PR states by the unique head/base/operation marker; exactly one matching result with the accepted head yields a receipt, multiple/mismatched results escalate, and absence after a lost request remains uncertain until authoritative failure is established. Never issue another POST merely because a list returned empty. Receipt: repository ID, branch ref, head SHA, tested base SHA, PR number/URL, and provider response identity. [GitHub pull-request API](https://docs.github.com/en/rest/pulls/pulls).

### Reference image factory v1

Definition ID `reference.image.v1`. Input: brief, output name, and tenant S3 destination. Reference brief: “One green oak tree on a plain white background, no text.” A Python runner uses Diffusers `StableDiffusionXLPipeline` with `stabilityai/stable-diffusion-xl-base-1.0` safetensors. The package lock captures an exact model repository revision plus every weight digest and dependency/image version; no remote custom model code executes. The official Diffusers documentation provides this pipeline/model path. [SDXL pipeline](https://huggingface.co/docs/diffusers/api/pipelines/stable_diffusion/stable_diffusion_xl).

Graph: brief snapshot → map four recorded seeds in explicit `collect` mode over isolated GPU generation → normalize PNG → deterministic checks plus protected semantic evaluation → choose the first accepted candidate in input order → acceptance → approval/policy → immutable S3 publication. Use seed inputs 11, 23, 37, and 53, 30 inference steps, guidance 7.5, width/height 1,024. Seeds are recorded inputs; no bit-identical GPU generation guarantee is made. Two candidate rounds maximum, with a revised prompt only in the second round. All failed variants remain auditable; no passing variant means rejection/escalation, not release.

Mandatory claims: exactly one decoded PNG frame, 1,024 × 1,024 RGB/RGBA, at most 10 MiB, no executable/extra embedded payload after normalization, and no recognized text from a pinned Tesseract English validator (no word with confidence at least 60). Three separate protected vision evaluations with `claude-haiku-4-5-20251001` return strict boolean fields `oneOakTree`, `greenFoliage`, `plainWhiteBackground`, `noText`. Require two complete PASS evaluations for every semantic field and no validator error/inconclusive result; missing/error results are rerun only within bounds, otherwise reject/escalate. Record common evaluator provenance and do not describe the quorum as independent confidence. Freshness is 24 hours for byte/format/OCR claims and 15 minutes for semantic claims.

Golden negative fixtures are a wrong-size PNG, an image with a large “SALE” caption, and an image of a car. Retain a human-reviewed tree fixture with expected semantic verdicts to detect evaluator/prompt regression; a real-model disagreement fails the domain gate for investigation. It is not retried until green by the test runner.

### Reference data factory v1

Definition ID `reference.data.v1`. Input: immutable UTF-8 CSV with header `record_id,category,amount_cents`, and tenant S3 export destination. Input must contain at most 1,000,000 rows and 256 MiB; `record_id` and `category` are nonempty strings; `record_id` is unique; `amount_cents` is a nonnegative decimal integer within the declared signed-64-bit domain. Reject malformed rows, duplicates, or accounting overflow; do not silently drop or coerce them. Snapshot the source version and content hash before expansion.

Graph: input snapshot → parse/schema validation → map ordered 10,000-row partitions to a pinned Python/PyArrow transform → explicit ordered reduction → protected reconciliation → acceptance → approval/policy → immutable S3 export. Output is a Parquet dataset with exactly the validated input rows, in input order, plus a manifest with row count, per-category counts, and exact integer amount sums. Serialization settings are pinned; acceptance checks values and manifests rather than assuming all Parquet writers emit the same bytes.

Mandatory claims: output schema matches the declared fields; row count and unique IDs match input; every row matches its source value; global and per-category sums/counts match exactly; no null/negative/overflow value appears; all partition indices appear once with no gaps. A separate validator recomputes these claims from the snapshotted input and exported Parquet, not the transform's self-reported counters. Claims stay fresh while the immutable input, validator, and environment remain pinned; any changed bytes/configuration requires a new decision.

Golden input rows: `(a, alpha, 100)`, `(b, beta, 250)`, `(c, alpha, 50)`. Expected output count 3, total 400, alpha count/sum 2/150, beta 1/250, IDs a/b/c in that order. Negative fixtures duplicate b, omit a partition, change 250 to 251, or overflow the amount domain. A deliberately defective transform can be repaired only as a new pinned child-plan/package revision inside the parent authority, then reevaluated against the original protected contract. Input correction creates a new input snapshot/run; it never rewrites the old snapshot.

### Shared S3 release adapter and cross-domain factory

Image and data use one `s3.immutable-publish.v1` adapter. Destination is an approved bucket/prefix and a deterministic operation directory containing the exact artifact files plus `manifest.json`. Never accept arbitrary endpoint credentials from the run. Stage immutable files with conditional create; verify their content checksums, media types, and object versions; conditionally create the final manifest only after all files verify. The manifest is the publication point. Release authority is scoped to that full destination/action/content set. A human-approved public prefix may expose these accepted bytes; staging is private and never constitutes public success.

Retry conditional creates only after verifying the old sender's outcome/generation. Existing identical content is reconcilable success; conflicting bytes are failure/uncertainty, never overwrite. The receipt lists every object key, content digest, version, and manifest digest. Do not treat an ETag as a content SHA-256. Verify conditional-write behavior with the actual store, including multipart data export. [S3 conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html).

Definition ID `reference.catalog.v1` composes the data child in acceptance-only mode, the image child in acceptance-only mode, then the code child to build a static catalog using their immutable accepted outputs. Input contains the CSV snapshot, tree brief, repository/base, and GitHub destination. Parent checks child contracts/digests, embeds the actual data/image bytes in the candidate tree, performs its own protected build/render tests and acceptance, then opens the authorized GitHub PR. Each child keeps its own budget; the parent cannot reset it or inherit child acceptance as automatic parent acceptance.

Other generators, repository types, image formats, schemas, destinations, merge/deploy actions, and streaming exports are extension points, not implied reference-pack support. ### Legacy workflow adapter v1

Definition kind `legacy.workflow.v1` wraps one pinned legacy workflow definition version as a factory task. It is opaque about internal steps and explicit about effects.

**Classification.** A legacy workflow may be wrapped only when it is classified non-publishing. The compiler classifies from the pinned definition version: every step's tool set must fall inside a static non-publishing allowlist, which excludes shell, MCP, `git`, any network-capable extension tool, and any nested workflow outside the allowlist. A workflow outside the allowlist may be wrapped only under a tenant-administrator attestation bound to the definition digest; any definition change invalidates the attestation. Wrapped runs execute under the fail-closed sandbox of C05 with egress limited to the tenant broker. C04's broker-only publication rule applies unchanged.

**Start and reconciliation.** The legacy engine has no caller-facing idempotency key today: the public run route accepts neither a key nor a run ID, the `workflow_runs.idempotency_key` column is reserved for the `nested:` shape, and a unique-key conflict on insert is caught by a bare catch in the executor and misclassified as `run-persistence-failed`. Stage 2b makes three legacy-engine changes, and only these: a caller-facing key in the `factory:` namespace, distinct from `nested:`, following the v4 bounded-key-plus-digest rule; discrimination of a unique-key conflict from a persistence failure in the executor's catch; and a periodic orphan sweep as a new sub-tick of the existing host maintenance daemon, since orphan recovery today runs only at web boot. The adapter journals the key under C02 before calling start; after a crash it looks the run up by key before starting again. An orphaned legacy run reaches a terminal or resumable state within the C11 detection bound.

**Status mapping.** `suspended` maps to factory `waiting` with its reason. A run orphaned at a batch boundary becomes resumable `suspended` and maps the same way. `awaiting_approval` is terminal in the legacy engine; it maps to a terminal uncertain outcome, is surfaced as a blocker, and is never resumed by the adapter. `running` with an expired lease is uncertain until the sweep resolves it. `error` with `resumable=false` (a mid-batch orphan or a failed step) maps to failed with the recorded batch index and in-flight step names. A run that stops because `workflowReleaseCanExecute` returns false mid-flight maps to failed with reason `release-authority-lost`; the adapter never re-grants authority. `done` maps to succeeded with the referenced outputs.

**Artifacts and jobs.** Legacy outputs and ez-factory `emit_artifact` files are not factory artifacts. The adapter may import one into the factory store only by a recorded copy whose digest is verified on write. The install-wide, ownerless ez-factory job store is never surfaced inside a factory project.

**F10 proof — signatures/fixtures in stage 1, real journeys in stage 5:** Each reference definition must compile and run with its real configured runner/provider/destination, pass a valid fixture, reject its negative fixtures, produce a new candidate on repair, and reconcile a lost release response. Wrap one allowlisted legacy workflow and one attested one; reject a shell-bearing workflow without attestation; kill the adapter between journal and start and prove no duplicate legacy run; drive each status-mapping row. Query the remote PR/object and verify its content identity. Run `reference.catalog.v1` through all three child packs. Retain real provider configuration/usage, remote receipt, screenshots, and acceptance evidence. Mocks are allowed for failure injection but do not replace the real provider/publication legs.

## C12 Hosted control plane and provisioning

The control plane is a separate trusted service for hosted operation, and nothing like it exists today: the repository has no Kubernetes manifest, no provisioner, and no tenant directory. It holds the tenant directory (tenant ID, hostname, installation identity, contact, plan limits, and membership references) and nothing else about customers: no artifacts, no provider secrets, no product facts. Its API is operator-only. No tenant route reaches it, and no route on it grants product access or consent.

**Provisioning** creates a tenant in this order, each step idempotent by tenant ID and recorded:

1. PostgreSQL database and role with a generated password.
2. Object-store prefix with prefix-scoped credentials, and a separately credentialed archive prefix in the other failure domain.
3. Temporal namespace with namespace-scoped mutual-TLS credentials.
4. Generated `EZCORP_JWT_SECRET`, `EZCORP_ENCRYPTION_SECRET`, and wrapped data key. The operator master key remains outside every grantable root.
5. Harness, orchestration process, and gateway deployments with those values delivered as secrets. Deliver the wrapped data key and operator master key only to the orchestration process as private Node secrets, and keep `EZCORP_SECRETS_DIR` outside every grantable root.
6. Ingress hostname bound to the installation ID.
7. First-administrator invitation; the first human login is the consent authority under C01.

A failed step leaves a recorded partial tenant that is either completed or torn down; it never serves traffic. The same provisioner, run once with local values, produces the self-hosted installation, so the two profiles share one code path. The installation checklist is a deliverable of this contract: it lists every operator prerequisite named in C05, C06, and C11 (container runtime and GPU driver pair, object-store license and credentials, key material, runner labels, alert evaluator), and readiness verifies each item it can observe.

**Fleet operations.** Migrations run per installation at boot, as today. The control plane upgrades installations in waves with a canary tenant; a migration or readiness failure in the canary stops the wave. Backups follow C06 per installation on a staggered barrier schedule. Upgrade order is fixed: supervisor and pool service, then orchestration processes with old build IDs retained, then harnesses and gateways. Rollback reverses that order and never drops a build ID that an active run references. Teardown tombstones the tenant, drains or fails its runs under C07, and leaves its release archive intact under C06.

**F12 proof — design in stage 2d, full proof in stage 6:** Provision two tenants with the provisioner and use them as the F01 installations. Provision 100 tenants for the F11 load run and record per-tenant resource totals. Fail each provisioning step and prove no partial tenant serves traffic. Run a canary-first upgrade wave with a deliberate migration failure and prove the wave stops. Tear down a tenant and prove its archive survives and its credentials no longer work.

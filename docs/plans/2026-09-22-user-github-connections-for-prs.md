## Outcome and v1 scope

A signed-in user connects one GitHub account at **Settings → GitHub**. The connection is available across that user's projects in this EZHarness instance, but each repository needs a separate GitHub installation/access check. The user can import a selected repository and base through the trusted host into their **private sandbox**, run an agent there, review the frozen change set, and confirm one draft PR. The host makes the authorized GitHub calls with a GitHub App user access token. No other application user, including an application admin or service principal, can view, use, replace, disconnect, or approve that personal connection or enter that private workspace.

The sandbox and model receive no GitHub credential. Connecting does not authenticate arbitrary `git`, `gh`, HTTP, or shell commands in the guest. V1 provides only host-brokered selected-repository import and confirmed draft-PR publication. It does not silently use a local host checkout or a project-wide token. A missing personal connection never falls back to a tenant, project, or Factory credential.

“Only the user” refers to application authorization. The trusted host must decrypt a token to call GitHub, so an operator who controls the host and encryption key remains inside the trust boundary. The product must state this accurately.

## Current seams and branch boundary

- On this checkout's `main`, `src/runtime/sandbox/controller/controller.ts` records a sandbox binding owner at creation, but its status gate accepts project membership. Native workspace execution also checks conversation ownership and binding revision. That is insufficient for a personal workspace: another project member can use their own conversation against the same project workspace. `src/runtime/workspace/target.ts` intentionally gives a sandbox target no host root. Sandbox creation currently accepts only an empty workspace and rejects `sourceProjectId`.
- `src/extensions/project-open-pr.ts` expects a local `projectRoot` and currently reads a whole checkout diff. It cannot directly publish from a sandbox container path. The [in-app PR plan](2026-09-20-simple-in-app-prs.md) proposes isolated run changes, the review card, and the shared publisher; it is still a plan, not a completed sandbox implementation. Its old project-credential language must be replaced by this personal contract.
- `src/extensions/secrets-store.ts` has host encryption, but its AAD does not bind `userId`. The generic `/api/settings/:key` route is admin-wide. Neither is an acceptable personal connection record. Use dedicated user-owned rows and session-only routes.
- The Factory contracts and release code are on `feat/composable-factory-platform`, not this checkout's `main`. Factory's `tokenPath` destination and immutable release branch need their own integration after that branch lands or is rebased. Personal Settings and personal sandbox PRs must be testable and shippable without claiming Factory's release guarantees.

## Authorization contract

For a personal PR, the connection owner, initiating run owner, conversation owner, sandbox binding owner, proposal owner, and confirming session user **must be the same stored EZHarness user ID** in the same instance. The run's project must match the sandbox binding's project. Derive every identity, repository, base, and workspace reference from persisted records; ignore caller-supplied IDs as authority. Check both project access and exact owner equality. Application admin rights, project membership, service identity, and consent by a different user grant no exception.

The run must use a private sandbox workspace that only its owner can read or modify through every workspace route, method admission, tool, status, export, and provider RPC. Deny shared project workspaces and local host workspaces for this personal path. The controller must close its project-membership-only access path for private bindings; a publisher check alone cannot stop another member from altering the source tree. Bind the run to a sandbox binding ID, provider resource incarnation, and workspace revision; a replaced binding or changed revision invalidates the proposal.

V1 gives each private sandbox one owner conversation. Later runs in that conversation
build on earlier changes. After the latest successful run, the user selects
**Prepare PR review** to freeze the cumulative change from the imported base.
Check that no newer run exists before and after export and at publication. The
current runtime has no structured check receipts bound to this artifact; display
**No verified checks recorded**. A successful run alone is not a passed test suite.
Personal publication uses the GitHub Git Database REST API. A future Factory
adapter must keep its separate authority and release policy.

The durable proposal records owner, connection authorization generation, GitHub numeric account ID, project/conversation/run IDs, private binding ID and resource incarnation, workspace revision, destination repository ID, base ref and commit, immutable exported artifact digest, title/body digest, expiry, and operation ID. The same user confirms that exact proposal in a live browser session. Recheck all of those fields, current owner/access, repository permission, and artifact bytes before dispatch. A later sandbox edit creates a new proposal; it cannot change an approved one. The [in-app PR plan](2026-09-20-simple-in-app-prs.md) defines publisher states, stable operation refs, receipts, and read-only reconciliation.

## Connection and repository journey

1. The operator registers one GitHub App for this self-hosted instance. Supply its App ID, client ID, client secret, exact public HTTPS callback URL, and private encryption key through host configuration. The callback must reach this instance; the public base URL and trusted proxy settings must agree. Enable expiring user access tokens and PKCE `S256`. Make the App **public** if users need to install it on accounts other than its owner; a private App cannot serve arbitrary user accounts. Allow installation on personal and organization accounts that fit product policy. Start with repository Metadata read, Contents write, and Pull requests write; verify permissions against every actual import and publish endpoint before registration. V1 rejects a change set touching `.github/workflows/**` and does not request Workflows write. Revisit this only with an explicit permission and test plan.
2. **Connect GitHub → authorize account → enable selected repository if needed → return to the original PR review.** Start OAuth only from a signed-in session. Store a short-lived, one-use state, PKCE verifier, instance/session binding, expected authorization generation, and an internal review return key on the host. Use an exact registered callback; accept no arbitrary external return URL. Exchange the code on the host, get the numeric GitHub user ID, and atomically install one connection for that EZHarness user. An aborted or failed reconnect leaves the prior valid connection intact.
3. Account authorization and installation are separate. At repository check, query GitHub with the current user token for the user's installations and selected repositories; also verify effective user and App permissions for the exact repository ID. Do not trust a callback `installation_id`, URL, login, or project setting as proof. Show distinct states: **account connected**, **repository not enabled**, **insufficient user permission**, **reconnect required**, and **ready**. The user API cannot prove whether an absent installation has an organization approval request pending. Offer the App installation link and an **I requested approval** action; label this as user-reported and keep access blocked. On return or recheck, query GitHub and resume review only when access is verified. If the user lacks write access, explain that they need repository permission; do not offer another user's token.
4. Store one current connection per instance/user with GitHub numeric account ID, App ID, encrypted access/refresh pair, expiries, authorization generation, token revision, state, and audit timestamps. Keep a tombstone generation even after disconnect so old callbacks cannot restore a row. Include instance, user, GitHub account, App, and token kind in ciphertext AAD. Return only safe account metadata. Keep the credential broker host-private, with no browser, guest, model, log, audit, or generic settings token path. Define encryption-key rotation and backup/restore behavior before rollout.

## Lifecycle and effect fence

Use one durable per-user coordination point for connection changes, refresh, and effect dispatch. The authorization generation increases on successful reconnect or account replacement and on disconnect; it does **not** increase on ordinary token refresh. OAuth attempts and proposals capture the generation. A callback may commit a new connection only if its attempt is unused, its session still matches, and the expected generation still matches. A callback that returns after disconnect or another successful reconnect is rejected; discard/revoke any token acquired during that stale attempt. Reconnecting even the same GitHub account requires a new proposal and a new human confirmation.

Serialize refresh against refresh, reconnect, and disconnect across processes. Under the same durable fence, compare the connection identity, generation, and token revision before saving both rotated tokens and expiries atomically. GitHub invalidates the old refresh **and access** tokens on refresh; if the response or commit outcome is uncertain, mark **Reconnect required** instead of restoring old tokens or guessing. A late refresh cannot overwrite a new connection or resurrect a disconnected one.

At the effect boundary, atomically claim the exact proposal and operation, recheck its generation and ownership, obtain a valid host-only token, and durably mark **dispatched** under that coordination point. Only then may the host send the write to GitHub. Disconnect increments the generation and blocks every write that has **not** passed that dispatch claim. Once a request may have been sent, local disconnect cannot recall it: retain the dispatched receipt and use read-only GitHub reconciliation for an uncertain outcome. Never retry that write with a replacement identity. Test interleavings by controlled barriers, not clocks.

## Private sandbox import and export prerequisite

Before a write run, the owner selects a repository and base that the host verifies using the owner's current connection. A narrow host-brokered import fetches that exact repository ID and pinned base commit into a new owner-private sandbox workspace through the provider boundary. Do not put a token in a remote URL, guest environment, Git config, command argument, archive, or log. If the provider cannot receive the import without exposing a bearer, refuse the operation. Bind the imported base, owner, run, binding ID, resource incarnation, and revision in durable state. Recheck access before import and again before publication; repository permission loss stops new effects.

At run completion, export a bounded artifact through the sandbox provider boundary: exact base identity, changed paths and bytes, statuses, limits, and digest. Validate paths, links, file types, size, `.ezcorp` exclusion, workflow exclusion, base consistency, and the digest on the host. Freeze the artifact in host-private storage before review. The shared publisher may reconstruct a private staging checkout at the pinned base or use a validated artifact adapter; it must never infer a host path from a sandbox path or read the sandbox again after confirmation. A different run cannot substitute an artifact, even within the same project.

## Acceptance gates

1. One personal connection serves A's authorized projects. A alone can manage it and use it from A-owned runs in A-owned private sandboxes. B, an admin, and a service principal cannot cross that boundary, even as project members.
2. A selected private repository can be imported at a pinned base without guest credentials. The reviewed artifact is immutable, bounded, host-validated, and tied to one run and sandbox incarnation. A complete real sandbox-to-PR path succeeds.
3. The user can authorize, enable a repository or request organization approval, return to review, and see a distinct permission failure. Only a verified installation and user permission enable the effect.
4. Disconnect and reconnect fence stale callbacks, refreshes, and proposals. Disconnect stops undispatched writes. Dispatched uncertain outcomes retain read-only recovery and cannot be promised immediate remote cancellation.
5. GitHub attributes a personal PR to the connected user. Factory autonomous PRs, when integrated, use only their separately approved tenant identity. No mode can switch credentials or silently fall back.
6. Source coverage, changed-line coverage, route and UI tests, e2e evidence, and the early real GitHub proof are green on the exact release commit.

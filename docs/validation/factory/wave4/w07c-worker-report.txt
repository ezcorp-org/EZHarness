2. ROOT CAUSE
-------------
prepare mints the id as `factory-release:${digestObject(identityFor(input))}`
(src/factory/releases.ts:664). identityFor (:380) digests projectId, runId, nodeInstanceId,
candidateGeneration, candidateDigest, action and the whole destination object including
expectedVersion.

The table has TWO unique indexes (src/db/schema.ts:3247):
  factory_release_operations_pkey            (tenant_id, project_id, operation_id)
  idx_factory_release_operations_identity    (tenant_id, project_id, run_id, node_instance_id,
                                              candidate_generation, action, destination_provider,
                                              destination_account, destination_object)

The id digests a STRICT SUPERSET of those nine columns (it adds candidateDigest and
expectedVersion). Two identical declarations therefore always collide on BOTH indexes.

PostgreSQL arbitrates only the index named in the conflict target. A conflict on the arbiter is
resolved by the DO NOTHING alternative; a conflict on any OTHER unique index is a plain constraint
violation. The statement named only the nine-column index. When two declarations of the same
logical operation both passed the arbiter pre-check before either had written its index tuple, the
loser reached speculative insertion and hit the primary key first (lower OID, written first), and
_bt_check_unique raised 23505 rather than converging. That window is microseconds wide, which is
why the case failed under load and passed alone.

The same logical declaration arrives twice concurrently in ordinary operation because prepare is
reached under two different HTTP idempotency keys, so the mutation-receipt layer does not
deduplicate them. The C04 case declares once as "concurrent-left" and once as "concurrent-right" —
the retry / two-worker / two-harness-client shape C04 requires to converge on one row.

The id is a deterministic digest, so no coordinator design decision was needed.


3. THE FIX
----------
One clause. The conflict target is removed so that EVERY unique index arbitrates:

  ... ON CONFLICT DO NOTHING

Converging is not the same as accepting. The exact durable reread that already followed the insert
(readInTransaction by tenant/project/operationId, then the requestDigest / materialDigest /
destinationDigest / deadlineMs equality checks) still decides identity, so C04 and interface
freeze section 11 hold unchanged:

  same declaration                          -> one row, both callers get the same identity
  same nine identity columns, different id  -> factory_release_conflict, refused by name
  same primary key, no matching identity    -> factory_release_corrupt, refused by name
     (corruption only; an id repeats only when every field it digests repeats)

No new identity, no widened acceptance, no interface change. FactoryReleases.prepare keeps its
signature and the id keeps the frozen `factory-release:` + 64 lowercase hex shape.


4. TESTS
--------
New producer: tests/postgres/factory-release-declare-race.test.ts (4 cases, real PostgreSQL only —
PGlite is a single connection and cannot hold two transactions open, so the barrier would deadlock).

The race is DRIVEN, not waited for. A BEFORE INSERT row trigger runs ahead of the ON CONFLICT
arbiter pre-check, so both declarations park there on a shared advisory lock. The test asserts
pg_locks shows exactly two blocked backends before releasing them, which proves neither has probed
the index nor written an index tuple. Measured against the UNFIXED code:

  forced race, width 1   before-deterministic-w1/   8 of 10 failed
  forced race, width 3   before-deterministic/      9 of 10 failed

Honest limit: the residual ~15% is the host descheduling one backend after the simultaneous wake,
not a weaker assertion. Wake order belongs to the host, so the forced race is strong evidence and a
poor gate on its own. Case 3 therefore pins the SAME property with no timing dependence at all: a
primary-key collision the identity index cannot see was red 3 of 3 before the fix (before-pkonly/,
received "unnamed" because the raw DrizzleQueryError carries no release error code — 23505 escaped
the store) and green after.

  case 1  two declarations released together return one identity and write one row
  case 2  a different operation sharing the nine-column identity is refused by name
  case 3  a primary-key collision the identity index cannot see is refused by name, never raised
  case 4  two operations cannot share a primary key, because the id digests a superset

Cases 2 and 4 also pass against the unfixed code (red-check/run-1.log: 2 pass, 1 fail). That is the
evidence that the arbiter widened and the contract did not.

F1 (MEDIUM, blocking) — the producer flaked under parallel execution, and the defect was MINE.
  parked() filtered pg_locks on locktype, classid, objid, objsubid and granted, but not on
  `database`. An advisory locktag carries MyDatabaseId, so the set that BLOCKS was already
  per-database while the set being COUNTED was cluster-wide; two concurrent runs of the file, each
  in its own database, counted each other's waiters and awaitParked failed its exact-match check.
  The validator measured 3 of 20 failures at width 3, all carrying the barrier message and none
  carrying 23505. A false red, never a false green.
  Fixed by adding
      AND database = (SELECT oid FROM pg_database WHERE datname = current_database())
  Proof at f2ed5c118, sweep2/: 20 runs at width 3 -> 20 of 20 exit 0, 80 pass / 0 fail; 20 runs at
  width 2 -> 20 of 20 exit 0. "the barrier never parked" appears in none of the forty logs.

2. AUTHORITY -- THE CENTRAL QUESTION
===========================================================================
Read FactoryVerifiedAttemptMaterials and every caller in full
(src/factory/release-s3-scope.ts:183-233 the class; :272-304 its one production caller,
S3FactoryManifestReleaseProfile.resolve()).

Who can name an attempt: only S3FactoryManifestReleaseProfile.resolve() in production. It does
NOT forward a caller-supplied attemptId. At release-s3-scope.ts:276-281 it derives
`scope.attemptId` from `verified.attemptId`, where `verified` comes from
FactoryPublicationProvenance.attemptForDecision (src/factory/release-publication-set.ts:159-184,
untouched by this package). That derivation joins `factory_protected_command_effects`
(kind='request-acceptance', decision='accepted' only) -> `factory_task_completions` ->
`factory_executions`, keyed on the caller's own tenantId/projectId/runId/decision.decisionId, and
resolve() further cross-checks the result against input.decision.nodeInstanceId/
candidateGeneration/candidateDigest (release-s3-scope.ts:277) before ever building a scope. A
candidate A's release profile can therefore only ever resolve the ONE attempt tied to whatever
already-accepted decision the caller names; it cannot substitute an unrelated attempt B unless B
has its own independently accepted decision, which is not a scope violation.

FactoryVerifiedAttemptMaterials.list() itself (release-s3-scope.ts:221-232): reads the NAMED
attempt's authority fresh via FactoryExecutionJournal.readAuthorityInTransaction
(src/factory/executions.ts:440-449, a plain `SELECT ... WHERE attempt_id=? AND tenant_id=? AND
project_id=? AND run_id=? FOR SHARE`, unmodified by this package), refuses with a single opaque
`factory_material_scope_denied` for an unknown attemptId OR any tenant/project/run mismatch (all
four cases hit the identical `if (!authority)` branch -- no side channel distinguishing "exists,
wrong tenant" from "does not exist"), then delegates to a freshly constructed
FactoryAttemptMaterials (W04's unmodified class) under that authority, which itself re-derives and
re-locks the FULL authority tuple in a second, independent transaction
(artifact-materials.ts:566-577 -> executions.ts:482-484,560-564) before returning only that
attempt's own rows, scoped further by operationId.

readAuthorityInTransaction does NOT filter by status or deadline_at -- a cancelled or expired
attempt is still found by name. This is pre-existing, unmodified W04/W03 behavior
(authorizeMaterialReadInTransaction's own comment: "It admits no effect, so it stays available
after the deadline", executions.ts:481), not something this package introduces or widens: reads of
already-sealed, immutable materials are documented to outlive an attempt's liveness elsewhere in
the codebase (e.g. physical-stop lookups use the same function to find a cancelled attempt by
design). The worker's own tasks/todo.md review states this reasoning explicitly and correctly.
Since attemptId reaching this reader is never caller-controlled in production (see above), this is
not an authority-widening path.

Independent scratch test (not in the worktree; not part of the worker's suite):
/tmp/factory-platform-evidence/w08b-validation/scratch/verified-attempt-materials-toctou.test.ts,
2 pass, 5 expect() calls (log: logs/scratch-toctou.log). Proves, against the real unmodified code:
  1. A concurrent grant re-admission landing in the gap between the reader's two internal
     transactions (readAuthorityInTransaction, then the delegated FactoryAttemptMaterials.list())
     is refused, not silently served under the now-stale authority -- because the second
     transaction's lockScopedRead re-checks the FULL tuple including grant_revision.
  2. The same attempt answers normally again once quiescent, proving the refusal is about
     in-flight staleness, not a wedged or corrupted attempt.
  3. Cross-check: feeding a manually-staled FactoryAttemptAuthority straight into
     FactoryAttemptMaterials.list() (the exact composition FactoryVerifiedAttemptMaterials builds
     internally) reproduces the same refusal.

Conclusion: no path found that lets a background release role read outside the accepted attempt's
own scope. A foreign, unknown, or cross-tenant/project/run attempt is refused by name with no
disclosure of partial matches; list() returns only sealed rows of exactly the named attempt/
operation; a release profile built for candidate A cannot list candidate B's materials by naming
B unless B is independently, legitimately accepted -- which is correct behavior, not a leak.

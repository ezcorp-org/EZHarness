2. Cause
The write path is serialised:
- task_add saves at docs/extensions/examples/task-tracking/index.ts:748, inside withLock (index.ts:1343-1346).
  Correction: an interim report said index.ts:752; the line is :748.
- In a v4 worker, withLock takes a host-held row lock: packages/@ezcorp/sdk/src/runtime/lock.ts:46-68 and
  src/extensions/runtime-locks.ts:57-81.
- The host write locks the conversation row (FOR UPDATE) and checks the expected revision in the same transaction:
  src/runtime/task-tracking-host.ts:154-163.
The stall: the extension runner read each worker's out and err FIFOs on Bun's file-system thread pool (one thread per CPU). Two live
workers on 4 CPUs fill the pool. The trace (E/host-trace-1/iter-3.log, sha256 a4e56eb4e8337072) shows:
- worker B takes the lock, reads and sends its write;
- worker A is refused once, and its retry never reaches the host;
- B's answer arrives only after the 30 s deadline closes both workers.
Result: revisions 2 of 3 expected, the CI signature. A passing run had no overlap. The trace lines were in the test helper and host only,
were never committed, and their diff is E/trace-instrumentation.diff.

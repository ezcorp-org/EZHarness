FAILURES, CAUSES, FIXES
1-3. The /tmp root marker (three tests)
  docs/extensions/examples/claude-design/lib/project.test.ts
    > findProjectRoot > returns the starting dir when no .git exists up to the filesystem root
    expect(received).toBe(expected): expected "/tmp/cd-nogit-…", received "/tmp"
  docs/extensions/examples/graded-card-scanner/postinstall.test.ts
    > findProjectRoot > falls back to the starting dir when no .git exists above
    expected "/tmp/gcs-postinstall-…", received "/tmp"
  src/__tests__/build-allowed-env-injection.test.ts
    > buildAllowedEnv — EZCORP_PROJECT_ROOT resolution > swallows findProjectRoot failure when run outside a git tree
    expect(received).toBeUndefined(): received "/tmp"
  Cause: a product defect. The SDK findProjectRoot, five private copies in the example extensions,
  and ai-kit's installer all accepted any path named .git. This host has an EMPTY
  /tmp/.git directory (owner dev, left by another session). `git -C /tmp rev-parse` reports "not a git
  repository", but the walk anchored at /tmp. So the host would inject EZCORP_PROJECT_ROOT=/tmp for any
  spawn below /tmp, and extensions would write .ezcorp data into shared /tmp.
  Fix: the SDK walk accepts only what git reads as a repository: a .git directory holding HEAD, or a
  .git file whose text starts with "gitdir:". A new SDK export, resolveProjectRoot, never throws. The
  five example copies (auto-note vault and postinstall, claude-design lib and postinstall,
  file-organizer postinstall, graded-card-scanner postinstall, task-stack) route through it. The ai-kit
  CLI keeps the SDK as a peer only, so it asks `git rev-parse --show-toplevel` with the caller's GIT_*
  variables dropped. The shared test helper markGitRepository replaces the empty .git fixtures in eleven
  test sites. The tests plant a stray empty .git inside their own temp tree, so the case holds whatever
  /tmp contains. One .git walk is unchanged: the host resolver src/extensions/project-root.ts:139. It
  accepts a root only where docs/extensions/examples exists, so a stray /tmp/.git cannot qualify.
  Same cause, outside the backend pool, also fixed: the SDK leg's test/fs.test.ts (its precondition
  threw "/tmp/.git exists") and the ai-kit leg's cli-install.test.ts ("throws when no git root found").
  Mutation proof: with the old existsSync walk restored, 6 tests fail across 4 files (logs/mutant-walk.log).

4-5. The pi_session hard expiry (two tests)
  src/__tests__/security/m4-hooks-cors-pi-session.test.ts
    > post-expiry branch does NOT set ezcorp_session from the legacy cookie
    > pre-expiry branch DOES promote legacy token to ezcorp_session
    expect(received).not.toBeNull(): received null (both)
  Cause of the red tests: the regexes matched the old `if (...) {...} else {...}` shape by indentation.
  Hook refactor 4b9351267 (2026-09-21) replaced the else branch with an early return, and they last
  matched at b1b302eb9. The product defect you flagged is real: web/src/hooks.server.ts compared
  Date.now() with Date.parse("2026-06-01T00:00:00Z"). That date has passed, so the promotion branch has
  been dead code since June while the code still read as a live window.
  Fix (documented policy, not a new config knob): the documented sec-M4 policy says that after
  2026-06-01 the legacy cookie is purged, not promoted. That state is now permanent, so the bridge is
  retired. retireLegacySessionCookie ignores and purges pi_session, never promotes it, and warns once.
  No date in code decides what the hook accepts. The m4 source gates now pin the retirement and forbid
  a calendar literal (Date.parse/new Date of a YYYY-MM-DD string) in the hook. The replicated decision
  table is removed. The web Vitest suite drives the real hook with no pinned clock: exactly one cookie
  operation (the purge), no re-issue, a /login bounce without session_expired, and one warning. Docs
  (authentication.md) and the openapi.ts comment are updated.

6. The "Unix socket path limit" (one test)
  src/__tests__/production-image-lifecycle-launch.integration.test.ts
    > long persistent state keeps the authenticated runner transport below the Unix-path limit
  The W15 label is wrong: it names the test, not the cause. The file passes alone. Six concurrent copies
  (the pool's shape) failed 1 of 24 with expect(exit).toBe(0): received 1, stderr
  "TimeoutError: The operation timed out." All socket paths were already short: the launcher's runner
  root is /tmp/ez-production-lifecycle-XXXXXXXX/s, and the runner's private socket is /tmp/ez-runner-*.
  Cause: scripts/verify-production-image-lifecycle.sh probed the runner ONCE with
  AbortSignal.timeout(1000). The runner answers /v4/inspect only after a Podman state query, whose
  latency follows host load. So a healthy runner was refused on a busy host.
  Fix: the probe reuses inspectProductionRunner from scripts/lib/production-lifecycle-client.ts (the
  inline copy of the transport call is gone). It waits within the launcher's readiness budget: one
  constant, readiness_seconds=120, used three times (socket wait, runner probe, health wait). A refusal, a wrong state, or
  a runner that exits still fails at once. A new test injects a 2-second delay on the runner's Podman
  state inspect through a fixture podman shim. The base script fails it with the same TimeoutError
  (logs/mutant-launcher.log). After the fix, 24 concurrent copies have 0 failures (receipts/fixed-launch-stress.json).
  This is not a widened tolerance: the one-second deadline was a wall-clock bound on host load, not a
  property of the runner. The probe now uses the same constant as the launcher's other two waits.

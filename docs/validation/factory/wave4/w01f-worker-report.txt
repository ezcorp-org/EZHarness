2. THE ROOT CAUSE, MEASURED ON BUN 1.3.14
------------------------------------------
The six detach lines were unreachable because Bun's node:http server delivers NO disconnect
signal at all. Every candidate was attached to the same parked exchange and the probe reports
which ones fired.

  response.on("close")                                    never fires, any close form
  request.on("aborted") / request.on("close") / "error"   never fires
  response.on("error") / response.on("finish")            never fires
  request.socket and response.socket events               never fires
  server.on("connection") socket close/end/error          never fires
  server.on("clientError")                                never fires

It goes further than silence. With the headers flushed and the body streaming - the exact shape
the brief asked about - five response.write() calls totalling 320 KiB into the dropped connection
all returned true and threw nothing, and response.writable stayed true. So a heartbeat whose write
can fail does not exist on this transport: that branch is unavailable, not merely slower.

The reason is visible in the internals: under Bun, request.socket is a synthesized
Symbol(fakeSocket) with no _handle, remoteAddress null, and readyState permanently "open".

Bun.serve DOES deliver the disconnect, as Request.signal:

  request.abort()                                  aborts
  request.destroy()                                aborts
  socket.destroy()                                 aborts
  host process SIGKILLed                           aborts, 12 ms
  half-close then the process exits                aborts,  9 ms
  half-close with the client alive and reading     does NOT abort

The last row is correct behaviour, not a gap: a client that half-closes can still receive its
answer, so it has not disconnected. The same six rows hold behind the real peer gateway.
The streaming ReadableStream cancel callback fires on exactly the same cases as the signal.

Receipts: logs/probe-node-http-signals.json, logs/probe-node-http-streaming.json,
logs/probe-node-http-internals.json, logs/probe-bun-serve-signals.json,
logs/probe-serve-through-gateway.json, logs/probe-dead-host-process.json.
Probe sources kept as probes/*.ts.txt.


3. THE FIX
----------
Serve the runner's private Unix socket with Bun.serve instead of node:http, and release the
attachment from Request.signal - the mechanism this runtime actually delivers. Nothing polls for
a disconnect and no timer guesses at one.

For the one form the runtime reports nothing for, the attachment became a lease, and the lease has
two distinct behaviours that an earlier draft of this report wrongly described as one.

RENEWING pushes the deadline one lease into the future. Only a request that proves the caller still
owns the stream may do it, because the protocol carries no host identity: /v4/events, which is
refused unless the session is attached and no poll is parked, and /v4/reply, which needs a pending
identifier only ever handed to the holder through that stream. /v4/attach starts the lease.
/v4/request does NOT renew, because any authenticated caller can issue one.

DEFERRING means the lease does not run at all, against an unchanged deadline: while the holder's
poll is parked (the runtime reports that disconnect directly), while the host owes a reply to a
queued reverse call, and while a forward call is executing. Each re-arms the lease when it drains,
so waiting one out never buys a host extra silence.

Both behaviours are validator findings F1 and F2, fixed here. A host waiting inside a long forward
call is no longer evicted mid-call; a second caller hammering /v4/request can no longer keep a
silent holder attached. And because an eviction can still be wrong in ways the service cannot see,
the shipped client now takes its stream back after a refusal it did not cause, bounded at three
consecutive recoveries so a worker that is really gone still ends the loop.

That re-arm is a correction to my own first version, and it was found by reading the CLIENT rather
than the service: RunnerClient collects an event, runs the host's reverse call, and only then
polls again, so the legitimate gap between two host requests is as long as that call takes, up to
the sixty-second host timeout. A lease that counted that gap as silence would have evicted a host
in the middle of its work. Removing the re-arm turns the busy-host case red
(logs/controlled-revert-lease-rearm.log), and the file was restored byte-identical.

Two declared settings, both validated against each other:
  eventPollTimeoutMs   default 20 000, range 100 ms to 5 min,
                       refused by name: RunnerError("event_poll_window", ...)
  attachmentLeaseMs    default 30 000, must exceed the poll window, at most 600 000,
                       refused by name: RunnerError("attachment_lease", ...)

A released attachment now answers nothing and keeps its whole queue. The previous code fell
through after detaching and spliced the queued NOTIFICATIONS out to a client that had already
gone, losing them; only the reverse calls survived. Making the detach path reachable is what
exposed that.

Test-only observation, exported from the module and never a global: startRunnerService now returns
RunnerService { close(), attachments(): string[] }. No endpoint exposes it and the wire protocol
does not mention it.

The v4 wire protocol is unchanged on every route and every refusal the protocol defines, with five
edge-case differences, none of which widens authority. "Byte-identical" was overstated and the
validator captured the exact set (F3; 25 of 30 raw captures are byte-identical):

  POST /v4/inspect?x=1                  base 404 unknown_method -> 200
  POST /v4/../v4/inspect                base 404 unknown_method -> 200
  POST http://runner/v4/inspect         base 404 unknown_method -> 200
  headers over 4096 bytes               base 431, no body       -> 400 request_limit, typed body
  two valid Authorization headers       base 200                -> 401

The first three follow from routing on new URL(request.url).pathname, which normalises, where the
base compared the raw request target. That is the conventional HTTP reading and it is kept
deliberately, but it IS a change. The fourth is the header policy moving from node's parser into
the handler, where it still runs before authentication, so nothing is bypassed; only the status and
the body changed. The fifth is stricter than the base: Bun joins duplicate header values with ", "
where node kept the first, so a request carrying two credentials is refused rather than having one
silently chosen. Every newly accepted spelling still passes the same bearer check and reaches the
same handler with the same validation.

Freeze section 6 (host launch, attach, stop) is untouched. RunnerClient changes only by gaining the
bounded stream recovery described above; its public surface is unchanged.

One control moved rather than lost, and one reason corrected. node:http's maxHeaderSize: 4096
becomes an explicit policy check in handle(), with its own test, because Bun.serve carries no
header option, and it still runs before authentication. maxConnections = 32 IS genuinely
duplicated: peer-gateway.py holds asyncio.Semaphore(32) and closes a connection outright when it is
locked, and the private socket is reachable only through that gateway and stays 0600 inside an
owner-only mkdtemp directory.

The earlier claim that the gateway's 360 s relay timeout duplicated headersTimeout was wrong, and
the validator measured why (F4): that timeout resets on every read, so it bounds nothing about a
slow header. The real fact is that Bun's node:http shim never honoured headersTimeout: 5000 at all.
Measured on a connection that sends a partial request line then goes silent, both trees close it
after the same interval: base 12 002 ms, this branch 12 003 ms. The control was already inert, so
removing it changed nothing measurable. That is the honest reason, not the one first given. Bun's
unix listener accepts no idleTimeout: its type rejects the option, which is recorded in the code.

8. ONE FAILURE OBSERVED, AND WHAT WAS DONE ABOUT IT
----------------------------------------------------
NO TEST WAS REMOVED. No test case, and no assertion, was deleted anywhere in this package. If you
were told otherwise, that is a misreading of an earlier draft of this section and the paragraphs
below give the git evidence. One assertion MOVED between two cases, and that is the whole of it.

What happened, in order.

The light sweep at 57a43bd54 recorded "8 pass / 1 fail" for
packages/@ezcorp/extension-runner/tests/service-detach.test.ts, while the same file had passed
seconds earlier in the same sweep and passed again in twelve re-runs afterwards, six of them
concurrent. The run is preserved at logs/observed-flake-light-suites.log. My sweep script did not
retain the failing file's output, so I could not read which case failed or what it said. That was
a defect in my own harness and it is fixed: the script now writes the full output of any failing
file to logs/postmerge-failed-<file>.log.

Without the output I had one usable fact: the runner's banner prints a total assertion count, and
the failing run printed 91 where a full pass printed 95. I measured the per-case counts by running
each case alone with -t (logs/expect-counts.txt: 32, 4, 5, 9, 15, 9, 8, 7, 6, summing to 95, which
matches the full-pass banner). A case that fails stops at the assertion that failed, so the failing
case executed four fewer assertions than it owns. Exactly two of the nine cases have an assertion
in the position that loses four:

  - "every host disconnect form releases the worker attachment and a replacement host attaches
    again", at its fourth assertion of eight per loop iteration, which was
    expect(refused.status).toBe(400) — a second /v4/attach expected to be refused while the first
    host still holds the stream;
  - "a host busy with a reverse call is never evicted while it still owes a reply", at its fourth
    assertion of eight, which was expect(harness.service.attachments()).toEqual(["worker"]).

Both of those assertions are true only while a short attachment lease has not yet expired, and at
the time both cases ran with a 600 ms lease behind several Unix round trips of setup. On a box
already running another worker's heavy producer, that lease can legitimately expire during setup,
and then the first assertion reads 200 instead of 400 and the second reads an empty attachment
list. In other words those two assertions were measuring how fast the host got through its setup,
not what the service does. tasks/lessons.md forbids exactly that.

So the dependence was removed, not the assertion, and not the case. Three changes, all in the test
file, none in the product:

  1. The default lease in the test harness went from 600 ms to 300 000 ms, so every case that is
     not about the lease now runs under a lease that cannot fire at all.
  2. The four cases that MUST observe a lease expiry ask for one explicitly, at 3000 ms, which no
     setup of a dozen Unix round trips can exhaust.
  3. The exclusivity assertion moved out of the disconnect table, where it ran once per drop form
     under a short lease, into "a dropped connection releases the attachment from the runtime's own
     signal, never from the lease", which runs under the five-minute lease. It is the same
     assertion against the same behaviour; it simply no longer sits behind a clock.

That is the entire diff of the timing-fix commit 869ab1542 as far as assertions go, and it is one
line:

    -      expect(refused.status).toBe(400);
    +    expect((await call(harness.socketPath, "/v4/attach", { workerId: "worker" })).status).toBe(400);

Three checks a validator can run in ten seconds, and what they return:

  - Case inventory. `git show 1fff3badf:<file> | grep -oE '^test\("[^"]+'` lists eight cases;
    the same grep at HEAD lists nine. All eight original names are present at HEAD, verbatim. The
    ninth, "a host busy with a reverse call is never evicted while it still owes a reply", was
    ADDED by 57a43bd54 together with the product correction it guards.
  - Assertion sites. `grep -c 'expect(' <file>` returns 43 at 57a43bd54, 43 at 869ab1542, and 43
    at HEAD. Not one assertion site was deleted.
  - The banner's drop from 95 to 92 runtime assertions is fully explained by the move, and by
    nothing else: the exclusivity assertion used to run inside a loop over the four drop forms, so
    it counted four times; it now counts once. 4 - 1 = 3, and 95 - 3 = 92.

Nothing was weakened, skipped, retried, or given a longer timeout. Ten concurrent copies of the
file then passed (logs/concurrent-stability.log), and the file has passed every run since,
including the whole post-merge sweep.

One honest limit on this account. I could not reproduce the original failure at the old setting -
twelve attempts, six of them concurrent, all green - so the identification above is an inference
from the assertion count, not a captured stack. I have stated it as an inference throughout and
kept the original failing run as evidence rather than discarding it. What is NOT an inference is
that both candidate assertions depended on a 600 ms lease surviving setup, that such a dependence
is a test measuring the host, and that the dependence is now gone from all nine cases.

packages/@ezcorp/sdk/src/v4/native-proxy.ts. So the change is CONSISTENT with the repository's
stated default; it does not resolve a rule the repository already imposed. Every existing assertion

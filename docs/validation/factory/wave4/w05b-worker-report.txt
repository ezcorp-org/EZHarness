FIX
- In its settlement transaction, FactoryUsageReconciliation.reconcile now calls clearResolvedStopInTransaction on the stop store, but only after it has settled the reservation from the receipt.
- That call sends the sealed stop's attempt-stopped event again, with the id <cancel>:usage-resolved, uncertain: false, and the settlement's own time. Sending it again produces the identical inbox event.
- Nothing is sent unless the physical stop is confirmed and its stopped event said uncertain.
- A hold whose usage is still unknown is not reconciled and not cleared.
- Reverse order, found on the real server: reconciliation settles the cost before the stop confirms.
  - Before the fix, the confirming stop failed factory_task_stop_stale for ever.
  - Now that stop keeps the settled budget and sends its own event with uncertain: false.
  - The stop store's re-derivation accepts that event shape when the latest settlement is a reconciliation.
- kernel.ts is unchanged, because the kernel already folds uncertain: false (W03e). A kernel test proves the clearing event ends the run once, that replaying all the events from the start gives the same state, and that redelivering the event is a no-op.

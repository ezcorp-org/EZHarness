5. THE LEASE, READ IN FULL AND INTERROGATED
=========================================================================

Mechanism (service.ts:109-123):
  attachHost()      sets attached = true and arms the lease
  renewAttachment() no-ops if not attached; else clears and re-arms a
                    setTimeout(attachmentLeaseMs) whose callback releases only
                    when session.pending.size === 0, and otherwise RE-ARMS
  releaseAttachment() clears the lease, sets attached = false, takes
                    session.wake, nulls it, then calls it
Renewal points: /v4/events (171), /v4/request (196), /v4/reply (158).
Re-arm condition: session.pending - the reverse calls the HOST still owes a
reply to. Each pending entry carries its own timeout of at most 60 s
(service.ts:137) and deletes itself, so the re-arm cannot loop forever: a truly
gone host is released one lease after its last outstanding call.

My own scenarios against the REAL service, none of which the worker's suite
runs: /tmp/factory-platform-evidence/w01f-validation/lease-scenarios.ts
Receipt: logs/lease-scenarios.json

S1 Declared settings and named refusals - PASS. eventPollTimeoutMs defaults to
   20 000, range 100 ms to 5 min, refused by the name "event_poll_window".
   attachmentLeaseMs defaults to 30 000, must STRICTLY exceed the poll window
   and stay at or under 600 000, refused by the name "attachment_lease".
   All seven out-of-range probes (equal to poll, shorter than poll, above ten
   minutes, non-integer, poll below 100 ms, poll above five minutes, poll NaN)
   were refused by the correct name.

S2 A host polling back to back is NEVER evicted - PASS. 24 consecutive polls at
   the shipped 1.5x ratio (500 ms poll / 750 ms lease): every poll 200, the
   attachment never dropped.

S3 A LIVE host inside one long forward /v4/request, with no parked poll -
   EVICTED. See F1. attachments() went ["w"], ["w"], then empty while the
   request was still in flight; the request still returned 200 but the host's
   next /v4/events returned
   400 {"error":{"code":"unknown_worker",...,"message":"Worker event stream is unavailable or already attached",...}}

S4 An owed reply re-arms - PASS. With a 750 ms lease the attachment survived
   2 600 ms (more than three lease periods) of host silence while one reverse
   call was owed; every sample read ["w"]; the reply was accepted 200, the
   reverse call resolved with its result, and the host's next poll was served.
   This independently confirms G7.

S5 Once the reply settles, silence releases within ONE lease - PASS. Released
   at 753 ms under a 750 ms lease.

S6 A NON-holder's request renews the holder's lease - CONFIRMED. See F2.

S7 Lease expiry racing an arriving request - PASS, no race. 60 rounds timed to
   land on the lease boundary, each firing /v4/events and /v4/attach
   concurrently: zero anomalies. Never two holders for one worker; never a poll
   served AND a replacement admitted in the same instant; no double release.
   This is structurally sound, not luck: the runtime is single-threaded, and
   parkEventStream's settle() nulls session.wake BEFORE calling
   releaseAttachment (service.ts:83), so the wake cannot re-enter and a second
   release is impossible.

9. FINDINGS, RANKED
=========================================================================

F1 (MEDIUM) - A live host inside one long forward /v4/request is evicted
mid-work, and the shipped client cannot recover from it.
  Where: packages/@ezcorp/extension-runner/src/service.ts:122
    session.lease = setTimeout(() => { if (session.pending.size === 0) releaseAttachment(session); else renewAttachment(session); }, attachmentLeaseMs);
  session.pending holds only the reverse calls the HOST owes a reply to. A
  forward /v4/request that the host is waiting on renews the lease once, at
  service.ts:196, and then nothing renews it for the rest of the call.
  Measured (S6 in logs/lease-scenarios.json, scenario S3): with a 750 ms lease
  and a worker method taking 2 500 ms, the attachment was released while the
  request was still in flight and the host's next /v4/events returned 400
  unknown_worker.
  Reproduce: bun /tmp/factory-platform-evidence/w01f-validation/lease-scenarios.ts <head worktree>
  and read S3_liveHostInsideOneLongRequest.
  Reachability through the first-party client is LOW but the consequence is
  severe. packages/@ezcorp/extension-runner/src/client.ts:41-59 runs its poll
  loop independently of request(), so a poll normally renews every <= 20 s
  against a 30 s lease. But that margin is only 10 s, on a box CLAUDE.md
  documents as routinely running six agents; and the loop is sequential, so the
  window opens whenever the host spends more than the remaining lease between
  one poll returning and the next starting with no reverse call outstanding.
  When it does open, client.ts:59 is
    void poll().catch(() => { closed = true; });
  so a spurious eviction permanently closes the host session client-side - there
  is no re-attach - and every later request() throws worker_closed.
  Suggested fixes, any one of which closes it: re-arm while a forward request is
  in flight; re-attach in the client on unknown_worker; or widen the default
  margin (C03 gives its own compute leases a 6x margin - 30 s lease renewed
  every 5 s - against the 1.5x here; C03 does not bind this package, but the
  ratio is a useful reference).

F2 (LOW) - "An attachment lease renewed by every request from the holding host"
is not what the code does, and unrelated traffic can defeat the half-close bound.
  Where: service.ts:158, 171, 196 all call renewAttachment(session) keyed only
  on workerId. The service keeps no per-host identity, so ANY authenticated
  caller naming that worker renews the lease.
  Measured (S6_nonHolderRenewsLease): the holder attached and then sent nothing
  at all; a different caller issuing /v4/request every 300 ms kept the
  attachment alive for 3 000 ms (four lease periods); it released 452 ms after
  that traffic stopped.
  Both callers are inside the same trust boundary (shared bearer token, same uid
  enforced by SO_PEERCRED), so this is not an authority hole. But it means the
  lease's bound on the half-closed-host case is not unconditional, and the
  report's wording should say "every request naming that worker" rather than
  "from the holding host".

F3 (LOW) - "The v4 wire protocol is byte-identical" is overstated. 25 of 30 raw
captures are byte-identical; five are not.
  Reproduce: bun wire-diff.ts in each tree, then diff logs/wire-base.json

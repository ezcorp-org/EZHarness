DEFECT 1: RE-GRANT AFTER REVOKE
Each grant is now its own row, numbered by grant_revision.
- The primary key includes grant_revision.
- A partial unique index, idx_factory_artifact_read_grants_active (WHERE revoked_at IS NULL), allows one active grant per target.
- A revoked row stays for audit. A new grant is a new row with the next number, never a reactivation.
- A still-active grant conflicts. A revoke reaches only the active row. A repeated revoke writes nothing.
- A first grant seals exactly as before, so existing rows still verify. Later grants also seal their number, so their audit ids never collide.
- Racing re-grants serialize on the revoked row. A racing first grant loses by name, through ON CONFLICT DO NOTHING.
- Migration allow-factory-artifact-regrant is appended to migrate(). Its test builds the old shape and holds a revoked row there. The upgrade keeps that row as grant 1, and a second run leaves every constraint oid unchanged. The restart suite has a case, and PostgreSQL schema parity checks the partial index.

DEFECT 2: DISPLAY NAMES
Grant records and the grant API resource carry displayName.
- It is the user's name or the service account's name, trimmed and cut at 256 characters.
- A blank name, a missing record, or a name equal to the id shows the stated placeholder "Unnamed principal", never the raw id.
- Only the name column is read.
- The list, read, set and revoke responses all carry it. FactoryGrants.displayNameOf serves the two mutations.
- The authorization path is unchanged.
- The SDK type FactoryGrantResource.displayName is required and 1 to 256 characters, and the response schema was regenerated.

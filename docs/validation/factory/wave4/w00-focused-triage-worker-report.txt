6. ROUND 3 — THE SWEEP WAS REJECTED, AND WHY THAT WAS RIGHT
------------------------------------------------------------
The validator accepted 698e9a2fb and rejected dc3eba210. It was correct, and the fault was my
verification method as much as my fix: I proved each swept file against ONE named victim and never
against the other files it shares a process with. Reproduced its findings before changing anything —
226 files (the four swept suites pull themselves into the auto list), 2787 pass / 4 fail, and both
minimal repros: executor-slash-command-expansion-e2e + mentions-search-symlink-integration =
17 pass / 1 fail; executor + mentions-search-workflow-branch + scratchpad-e2e = 25 pass / 3 fail
(<receipts>/repro1-before.log, repro2-before.log).

WHAT I GOT WRONG. Round 2 moved three stubs off `$server/*` aliases onto relative paths, reasoning
that native resolution carries a relative mock to the route. It does — but ONLY while no file has
registered the alias, and a dozen suites in this pool register `$server/db/queries/projects`,
`mockServerAlias()` among them. Once any file registers a `$server/*` specifier it is served from
that registration for the rest of the process, so the route kept calling the real `getProject` and
the suite's stub never reached it. The rule is narrower than I wrote it:

  a relative-path mock is right ONLY for an alias nothing in the pool claims;
  for an alias the pool DOES claim, the suite must claim it too — completely (spread the real
  module, so no export is deleted) and reversibly (re-register the real module in afterAll).

`$server/db/connection` is the one alias no suite claims any more, so its relative mock stays.

FIXED THIS ROUND (test-only, no assertion changed, no suite's own count changed):
  - Both mentions suites claim `$server/db/queries/projects` again, spread and reverted.
  - Both DROP their `$server/db/schema` stub entirely. Reverting it is not enough and cannot be:
    the route module is linked ONCE per process, so whichever suite imports it first binds its
    `extensions`, and re-registering an alias cannot rebind an import already resolved. An empty
    table then reaches a later suite's real drizzle query as `Object.entries(undefined)` inside
    `orderSelectedFields` — failure 2's exact signature. The stub was never load-bearing: the fake
    `getDb()` ignores whatever table it is handed.
  - `serverContextStub()` in helpers/mock-request.ts — every export of web's server context, inert,
    with the suite's overrides spread on top. Three suites stubbed that alias partially and so
    DELETED `getGoalHost` for the process, after which executor-slash-command-expansion-e2e could
    not link. The real module cannot be loaded from a bun test (its whole import graph is
    `$server/*` and `$lib/*`), so completeness has to come from a shared list kept beside it.
  - `$server/runtime/ez-actions/registry` spread in the workflow-branch suite; it had deleted
    `getEzAction`.
  - executor-slash-command-expansion-e2e no longer repeats `$server/db/queries/projects`.
    Stated plainly: deleting that line does NOT lift the freeze — `mockServerAlias()` on the line
    above and ten other suites still claim that alias, which is exactly why claim-and-revert, not
    relative paths, is the only composable pattern for an alias a route resolves.

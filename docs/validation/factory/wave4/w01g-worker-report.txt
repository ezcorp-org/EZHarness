2. WHAT THE GAP ACTUALLY WAS
----------------------------
Not one missing function. A missing route.

A sandboxed guest runs on --network=none, so W04's material service — which is
HTTPS on the execution gateway — is unreachable from inside it. The reverse
control frame is the only byte path a guest has, and it carried exactly one
payload, the model request (W01e). On the other side, W09b's supervisor-services.ts
records in its own header that the transport from a host back to the product is
undefined and that a guest's broker call therefore refuses by name with
factory_host_broker_unavailable.

So the work was three things: define the staging frames, answer them on the
host under the attempt's own verified authority, and carry them from the host
process that runs the container to the product process that holds the tenant
database.

5. THREE THINGS THE FIRST END-TO-END RUN TAUGHT
-----------------------------------------------
Each had already passed a unit test.

A sealed material has TWO digests, and confusing them is silent. The handle
covers the chunk manifest the scoped reader resolves; the content digest covers
the bytes. Both are "sha256:" and 64 hex. stageOutput now returns both rather
than the handle alone, and a promotion names the content — which is what the
first run caught.

A COMPLETED result cannot name a material. verifyCompletedEvidence loads the
output as kind candidate_output, bound to the attempt's own node instance and
generation, and re-parses it as canonical I-JSON. So the promotion reads the
sealed bytes back through the scoped reader, requires canonical I-JSON through
artifactJson.parse (the SAME rule applied on the way back out, called rather
than restated), and stages them through W04's own
stageCandidateOutputInTransaction, whose coordinate makes a repeat after a lost
response return the same reference and different bytes conflict. NOTHING IN
W03's VERIFIER CHANGED.

A completed result also needs a workspace checkpoint whose journalCursor equals
its own, and an attempt that settled no operation has cursor -1 — which W04's
FactoryWorkspaceCheckpoints.objectName refuses, because its names are operation
indexes. The guest names that one workspace/attempt.json and stages a real
sealed material, so the reference points at bytes rather than at nothing.


6. AUTHORITY: WHAT A FRAME CARRIES
----------------------------------
Nothing but the attempt token, exactly as ruled.

A frame names an operation id, an operation index, an object name and a
version. Every scope field — tenant, project, run, attempt, node instance,
candidate generation — is read from the verified attempt, either from
factoryRunnerRequestAuthority(request) in process or from the verified attempt
token on the wire. The material service rechecks the journal's liveness fence
inside each of its own transactions, so the adapter adds no authority and no
bypass.

The request digest the journal matches on is the TOKEN-FREE canonical identity,
so a token reissued on recovery still names the same durable attempt. A test
asserts that equality directly.

On the wire, two independent facts authorize one frame and neither is the
frame: the mutual-TLS peer identity says which host may drive attempts, and the
attempt token says which attempt the frame belongs to. The token travels in the
request body because the Authorization header already carries the host's own
service credential and both facts are needed; it is never logged. In the proof,
the product side names the SUPERVISOR's own certificate identity
("supervisor-w09b") as its allowed peer — a tenant client certificate on a
runner host is exactly what C01 and C02 forbid.

Refusals are named, never thrown as transport faults: a refusal turned into an
error would make "your attempt was superseded" indistinguishable from "the
product process is down". The vocabulary is invalid_request, unknown_attempt,
unknown_material, deadline_expired, stale_epoch, oversize, digest_mismatch,
chunk_out_of_order, sealed, conflict, operation_full,
output_not_canonical_json, unavailable.

stale_epoch covers the whole liveness fence in one name — run epoch, execution
epoch, cancellation epoch, reservation generation, grant revision and admitted
status — because the journal refuses them together in one UPDATE and telling
them apart would need a second read under authority this adapter does not hold.
That is documented on the type rather than left to be inferred.


7. BOUNDS, AND WHY THEY ARE SMALL
---------------------------------
FramedExecution.received counts every byte a guest writes for the LIFE of the
worker and podman.ts caps the ceiling at min(limits.outputBytes, 1 MiB). It is
a lifetime budget, not a per-frame one, so chunking buys nothing beyond the
frame bound and the TOTAL is what has to fit.

   maxChunkBytes   32 KiB   (= FACTORY_PAGE_BYTES_LIMIT, asserted equal in both
                             runtimes, so one canonical base64 codec carries a
                             chunk instead of a second encoder per language)
   maxChunks       64       (C02's own material chunk cap)
   maxTotalBytes   512 KiB  (683 KiB as base64, inside the 1 MiB lifetime
                             budget with room for the result frame)

W04's material service still bounds a material at 256 MiB. A runner that
reaches the gateway over private HTTPS may use all of it; a sandboxed guest has
only this channel. The difference is the transport, not the contract, and the
type says so.

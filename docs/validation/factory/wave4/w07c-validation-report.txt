2. THE SAFETY ARGUMENT — SOUND
------------------------------
Enumerated from the LIVE database after the committed migrations ran, not from the source
(evidence: probe-constraints.log; probe at tests/postgres/probe-constraints.ts in the scratch
worktree, whose src/db/ is byte-identical to the branch head):

  UNIQUE ARBITERS: exactly 2
    factory_release_operations_pkey
      PRIMARY KEY (tenant_id, project_id, operation_id)
    factory_release_operations_tenant_id_project_id_run_id_node_key
      UNIQUE (tenant_id, project_id, run_id, node_instance_id, candidate_generation, action,
              destination_provider, destination_account, destination_object)
  partial unique indexes: 0      exclusion constraints: 0      non-internal triggers: 0
  CHECK constraints: 20          foreign keys: 2

An untargeted ON CONFLICT DO NOTHING suppresses only unique and exclusion violations. The 20 CHECK
constraints and 2 foreign keys still raise, so widening the arbiter cannot silence a malformed row,
a bad state value, a bad digest shape, or a dangling decision or run reference.

What a suppressed conflict on each arbiter means after the fix:

  (a) the nine-column identity index, different operation id
      The reread is keyed on (tenant_id, project_id, operation_id) with the CALLER'S id
      (releases.ts:684, readInTransaction at :1154). No row comes back, so prepare raises
      factory_release_conflict at :685. Identical to the behaviour before the fix, because the old
      conflict target named exactly these nine columns and already suppressed here.

  (b) the primary key
      The reread returns the row stored at the caller's id. operationFromRow (:396) calls
      assertOperation, which re-derives the identity from the ROW'S OWN columns and refuses:
        operation.operationId !== `factory-release:${digestObject(identityFor(operation))}`
          -> FactoryReleaseError("factory_release_corrupt")            (releases.ts:426)
      A row that survives that check provably carries the caller's identity, under SHA-256
      collision resistance. prepare then compares requestDigest, materialDigest, destinationDigest
      and deadlineMs and raises factory_release_conflict on any mismatch (:685).

CAN A GENUINELY DIFFERENT OPERATION (different identity, different id) BE SWALLOWED AND READ BACK
AS THE CALLER'S?  NO. A different id is unreachable by a reread keyed on the caller's id, and a
matching id is proved by :426 to carry a matching identity. There is no third arbiter and no
partial index, so there is no other way for a row to be suppressed. No path returns the wrong row
silently.

The fix's ONLY behavioural delta: a pre-existing row at the caller's id whose columns do not match
that id used to raise a raw 23505 and now yields the typed factory_release_corrupt. That is
strictly better, and it is what test case 3 pins with no timing dependence.

Newly reachable path, checked: the losing declaration now proceeds past the insert to
insertTransactionalAuditEntry (src/db/queries/audit-log.ts:12), which is
ON CONFLICT (id) DO NOTHING on the deterministic id `factory-release-prepared:${operationId}`, so
convergence is idempotent there too. Both callers take FOR SHARE on the same row, which is
compatible, so there is no deadlock.

Observation, PRE-EXISTING and NOT introduced by this fix (finding 4): the reread's equality set
omits estimatedSpendMicros and the profile digests, so two declarations identical in identity,
request, material and deadline but differing in spend estimate converge on the first row. The old
nine-column arbiter already suppressed that insert on the sequential path and the same reread
returned the same row, so the base and the head behave identically. decisionId IS covered
transitively: validateMaterial binds material.decisionId to input.decisionId, and materialDigest is
hash(material). Out of W07c scope; raised for the record.

FINDING 1 (MEDIUM) — the new producer is flaky under parallel execution.
  tests/postgres/factory-release-declare-race.test.ts:23 and :55-58
  BARRIER_KEY is a module constant identical in every process, and parked() counts pg_locks rows
  filtered on locktype, classid, objid, objsubid and granted but NOT on the database column.
  pg_locks is cluster-wide, so two concurrent runs of this file each see the other's waiters;
  awaitParked demands exact equality and throws
      "the barrier never parked 2 declarations; observed 4".
  The file's own comment at :22 claims the opposite: "every test owns a freshly created database,
  so it cannot collide with a peer". The advisory LOCK is per-database and does not collide; only
  the COUNT leaks, so the barrier still forces the race correctly and the fix's evidence stands.
  Measured: HEAD width 3, 3 of 20 runs failed, all three with the barrier message and none with
  23505. HEAD width 1, 0 of 20 failed. The worker never saw it because their post-fix runs were
  width 1, and pre-fix it was masked by the 23505 failure.
  Reproduce:
    /tmp/factory-platform-evidence/w07c-validation/run-pg.sh \
      /home/dev/work/EZCorp/EZHarness-worktrees/composable-factory-platform/.worktrees/w07c-declare-race \
      20 3 /tmp/out ./tests/postgres/factory-release-declare-race.test.ts \
      "two declarations of the same operation released together"
  Fix: add
      AND database = (SELECT oid FROM pg_database WHERE datname = current_database())
  to the pg_locks predicate. Advisory locktags already carry MyDatabaseId, so the blocking set and
  the counted set then agree. One line, and the stale comment at :22 becomes true.
  This is a false red, never a false green: it cannot hide a regression, only make CI flaky.

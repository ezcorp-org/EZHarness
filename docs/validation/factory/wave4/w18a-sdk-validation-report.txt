      executable lines and BOTH are covered. Coverage went up, not down.
      (base-service.log, head-service.log, coverage/runner-partial.lcov)

  (c) The unreachability claim is true, and I verified it myself rather than taking it.
      My first probe, registering the handlers while the request stream was still open,
      DID fire "aborted" for three of four close forms — so the claim is not trivially
      true and deserved checking. But service.ts drains the whole body
      (`for await (const chunk of request)`) BEFORE it registers response.once("close")
      and request.once("aborted"), and Node does not emit "aborted" after a message has
      ended. Reproducing that exact order under bun 1.3.14:
        request.abort()     -> neither handler fires
        request.destroy()   -> neither handler fires
        socket.end()        -> neither handler fires
        socket.destroy()    -> neither handler fires
      detach is genuinely unreachable from any test in this repository.
      (bun-detach-probe.ts / detach-probe.log, bun-detach-probe2.ts / detach-probe2.log)

  Conclusion: the alternative to keeping the case inline was to put six provably
  unexecutable lines into the patch-coverage gate's view, which could only be answered by
  a fake assertion or a weakened gate. The worker took the honest third option, left the
  behavior untouched, and reported the gap. I would have done the same.

  The worker's PRODUCT QUESTION is real and my probe confirms it: under Bun a host that
  drops its event stream never releases the worker's attachment (session.attached stays
  true), so no replacement client can reattach. That is a latent runner defect, correctly
  flagged, correctly left out of a complexity refactor's scope. It belongs to the runner's

## Findings, ranked by severity (full detail with file:line and repro commands also in results.json)

**Finding 1 — medium, test flakiness under host contention (not a code regression).** My first full run of `packages/@ezcorp/extension-runner/tests/podman.integration.test.ts` failed "a SIGKILLed supervisor leaves one guest that a fresh supervisor attaches and cancels" (`podman.integration.test.ts:86-111`) with `RunnerError: worker_not_running` thrown from `attach()`'s internal `inspect()` call at `packages/@ezcorp/extension-runner/src/podman.ts:283`, even though the test's own preceding `inspect()` assertion had just observed `state: "running"`. I found a concurrent, legitimate process (PID 4117720, since exited) re-running the worker's own `merge-lcov`/`receipt.sh final-static-gates` pipeline in the same worktree at the same time, consistent with the `w01-runtime` agent still being active. Reproduction: `flock /tmp/ezcorp-validation-heavy.lock bun test --timeout 300000 ./packages/@ezcorp/extension-runner/tests/podman.integration.test.ts`. Isolated retest (`-t "a SIGKILLed supervisor leaves one guest"`) passed 1/1, and a second full-suite run passed cleanly (14/14, 75 assertions, matching the worker's receipt exactly), with zero leftover containers before or after either run (`podman ps -a`: 54 before, 54 after). This is a real timing-sensitivity in the gap between a supervisor's `SIGKILL` and a fresh runner's state check under host load — the property itself is correct and reproducibly provable, but the test has no retry/poll margin. Recommend: add a short bounded poll (e.g. retry `inspect()` for up to ~1s) before asserting `state: "running"` in this test.

**Finding 2 — low, documentation accuracy.** `/tmp/factory-platform-evidence/w01/INDEX.md` claims the focused-suite receipt has "208 assertions." The worker's own raw log at `/tmp/factory-platform-evidence/w01/logs/final-focused-suites.log` shows **212** `expect() calls`, exactly what I reproduced independently. Not a pass/fail discrepancy — just an undercount in the summary document. Fix: correct the number in `INDEX.md`.

**Finding 3 — medium, missing regression test for a required plan clause.** The plan's W01 pass criteria require that "API failure or timeout never proves physical absence." I confirmed by code inspection that `stopPhysical()` (`attempt-runtime.ts:570-583`) and `open()` (`attempt-runtime.ts:416-421`) never catch-and-reinterpret an `inspect()` rejection as absence — an exception propagates uncaught rather than being coerced into a stop/replace decision. However, **no test anywhere in the landed suites makes `inspect()` reject or hang** to prove this; every test double's `inspect()` always resolves to a definite state. A future refactor that wraps `inspect()` in a try/catch defaulting to "not running" would pass every existing test today. Recommend: add one test per suite layer (unit and Podman-integration) that makes `inspect()` fail/time out and asserts the attempt is neither stopped nor replaced, only left `uncertain`.

**Finding 4 — medium, plan bullet only half-provable within W01's scope.** The plan requires proving "replacement on a different compute host occurs only after signed physical-stop... proof and fencing/reconciliation." W01 thoroughly proves the *production* half: `attempt-runtime.integration.test.ts:116-121` performs a real RSA sign/verify round-trip via `node:crypto` over the canonical unsigned facts, and `stopPhysical` refuses to sign a receipt unless a prior terminal `inspect()` observation confirms the state. What is not implemented or tested anywhere in what W01 landed is the *consumption* half — a component that actually refuses a cross-host replacement decision when a valid signed receipt is absent, forged, or stale, with `holderGeneration`/`hostId` fencing enforced before that replacement. That authority correctly belongs to `src/factory/task-stops.ts` / `src/factory/pool/ledger.ts`, assigned to W03 (Sol lifecycle) by the interface freeze and unmerged on `integ/w00`. Not a false claim by the worker — `tasks/factory/w01-GATES.md` G9's evidence text only claims the signing/verification half — but the plan's own W01 checklist names the full topology, so the coordinator should track this as an open cross-package dependency rather than a closed item, and confirm W03 actually gates on it when it lands.

**Finding 5 — medium, disclosed freeze deviation needing sign-off.** The freeze (section 6) recommends "Terminal result storage default: reuse `factory_execution_terminals`... No new table." The worker instead stores the terminal result in two new columns on `factory_attempt_launches` and explicitly flagged this as a deviation in `tasks/todo.md`'s Review paragraph — correctly disclosed rather than silently forked. I confirmed: no new table was created; `factory_execution_terminals` (written by `src/factory/executions.ts:314`) requires a verified output-artifact FK and NOT-NULL output bytes/digest, so it structurally cannot hold a failed, cancelled, or uncertain runner result, which is a legitimate reason to diverge; and no other landed consumer currently expects per-attempt runner results in that table (W03's stop authority reads `factory_task_outcomes`, not `factory_execution_terminals`). Recommend the coordinator formally amend the freeze to match rather than leave this as a standing deviation.

**Finding 6 — low, minor interface-shape mismatch to track.** `FactoryHostLaunchProtocol.stop` in the landed code takes W01's own `FactoryPhysicalStopRequest` (attemptId/reservationId/holderGeneration/reason), not the freeze's richer `FactoryTaskStopRequest` (hostId, allocationGeneration, cancelReference, attemptReference, workerId, source) — unavoidable since `FactoryTaskStopRequest` is W03's unmerged type. `FactoryHostLaunchProtocol` itself has no call sites yet. Flag for reconciliation when W03 lands; not a defect today.

**Finding 7 — informational.** Per-attempt device grants are fully modeled, validated, and persisted at the database layer, but `packages/@ezcorp/extension-runner/src/podman.ts`'s actual container-launch code still reads the host-global `configuredDevices` rather than `input.devices`. This is exactly what the freeze specifies for this wave ("Behavior unchanged: every device list stays empty until W02"), so it is not a gap in W01's own scope — but the coordinator and W02 should be aware that "device grant closed" means the data model and validation are closed, not that per-attempt device enforcement is wired end-to-end yet.

**Finding 8 — informational.** `scripts/check-factory-boundaries.ts` (nominally coordinator-owned) gained not just new `REQUIRED_SHARED_IMPORTS` rows but also a new `WORKSPACE_PACKAGE_ENTRIES` resolver — a real logic change to a shared gate file, needed to make bare-specifier workspace imports resolvable at all, and covered by a paired new test. Reasonable and tested, but flag for coordinator awareness since the file is jointly touched.

**Finding 9 — informational.** The device grant's `holderGeneration`/`hostId` staleness check is enforced (a re-validation against the current lease recomputes `grantDigest` and rejects on mismatch, `attempt-runtime.ts` around line 314-317) but there is no test with an explicit "stale lease" name/assertion exercising exactly that path — only an indirect digest-change assertion. Recommend one named test for clarity and future regression safety.

## Security posture

No authority check was removed. The two apparent removals (`supervisor.ts`'s local `reverseEnvelope()`, `podman.ts`'s monolithic `probe()`) are DRY refactors into equivalent-or-stricter shared logic (`guest-frames.ts`'s `factoryGuestFrameInput`, and `prepare()` + `probeSecurity(cleanupOrphans)`), not weakenings — I traced both replacements and confirmed the new code enforces the same or stricter checks. No credential value appears anywhere in the evidence directory, logs, or scripts; `postgres-env.sh` builds the connection string at runtime and never echoes it. The guest container's environment carries no database or S3 credential, and the host RSA private key used to sign stop receipts is held only by an injected host-side closure — product/guest code never receives it. Guest-control-frame binding (worker/invocation/attempt triple, oversized frame, >32 pending, method allowlist) is exhaustively tested with a table-driven drift matrix.

# Extension v4 contracts

Marketplace versions store a separate `PublishedExtensionRelease`. It binds the verified runner build, original source, per-file checksums, and release digest. `sealPublishedRelease` verifies the runner artifact before removing runner-only files; `validatePublishedRelease` checks the stored source and catalog before import. Metadata queries do not return the source payload. Import stages the source for a fresh isolated build and human approval; publishing never grants runtime authority.

This package owns data types and runtime validation. It does not import the host, database, or SDK. Legacy SDK types re-export these shared declarations.

`validateWire(kind, value)` checks the full data shape and rejects unknown fields. Use `validateManifest`, `validateWorkspaceFiles`, `validateResourceLimits`, and `validateInvocationContext` for their additional semantic checks. Validation does not grant permission or establish trust in build evidence. The host must compute and compare release digests itself.

`canonicalJson` and `sha256` provide one content digest format: sorted object keys, ordered arrays, and a lowercase SHA-256 hex string. Source maps are limited to 2,000 relative text files and 20 MiB of UTF-8 content. Empty workspaces are valid. Traversal, control characters, reserved keys, `.git`, and `node_modules` paths are forbidden.

Sandbox provider extensions declare optional `sandboxProviders`. Each provider advertises only the fixed `linux-exec.v1` and `persistent-web-compose.v1` profiles and supplies at least one complete preset for every advertised profile. Presets are closed data. They bind lowercase SHA-256 image, recipe, and helper identities plus storage, network, limits, compatibility requirements, and numeric override bounds. Unknown fields, credentials, moving image tags, duplicate identities, unsupported profiles, and incomplete Compose controls fail manifest validation. Manifests without sandbox providers remain valid.

Preset-only sandbox declarations remain valid for wire compatibility. A provider entering conformance must also supply the complete contribution fields checked by `validateSandboxProviderContribution`: kind and protocol, minimum host contract, configuration schema, declared permissions, and exactly one `sandbox.provider.v1` group. Legacy contributions can keep only `describe` and `preflight`. A provider that advertises the stable protocol capabilities must map every lifecycle (`create`, `inspect`, `list`, `setPower`, `destroy`, `inspectOperation`), file (`stat`, `list`, `readRange`, `writeAtomic`, `remove`), and process (`start`, `inspect`, `readOutput`, `cancel`) method. Endpoint `open` and `close` mappings are present only with `endpoints.v1`. Snapshot, restore, suspend, PTY, and resize remain separate optional capability identifiers and are not methods in this stable v1 surface. Every mapping names a unique non-tool runtime method using the schemas returned by `sandboxProviderMethodSchemas`.

The protocol uses host-issued stable IDs and explicit connection and sandbox scopes. Mutation inputs carry a request ID and idempotency key. Asynchronous lifecycle, removal, cancellation, and endpoint-close results return an operation receipt; `inspectOperation` reports desired and observed state without turning an unknown outcome into success. `OUTCOME_UNKNOWN` requires a stable operation ID and forbids blind retry. RPC deadlines are absolute milliseconds. Process deadlines are separate and can extend at most 30 days beyond the RPC deadline.

File paths are relative workspace paths bounded to 240 UTF-8 bytes; `.` is the explicit root for stat/list operations. Directory lists return direct children only. Reads are revision-bound ranges of at most 64 KiB. Writes are canonical base64 chunks of at most 64 KiB, compare an expected revision (or `null` for create), and atomically replace one file. Large staged transfer is not part of v1. Process starts bind argv, environment, user, working directory, and execution deadline. Output reads use a sandbox/process/boot-bound monotonic byte cursor, return at most 64 KiB, and report every missing range as an explicit gap. Lists use revision- or connection-bound cursors and return at most 100 entries. Endpoint URLs must use HTTPS, fit within 2,048 UTF-8 bytes, and preserve an approved valid UTC expiry no more than 24 hours after the RPC deadline.

`describe` must match the reviewed provider, profiles, preset IDs, and declared capabilities. `preflight` returns a bounded backend observation; it does not decide compatibility or grant authority. Call `assertSandboxProviderOperationSupported` before dispatch so absent optional capabilities fail with `UNSUPPORTED_CAPABILITY`.

`resolveSandboxPreset` is the authoritative pure selection path. The caller supplies an exact provider, profile, preset ID, backend observation, and optional numeric limit overrides. The resolver does not choose another preset or profile. It rejects unsupported API, architecture, storage, isolation, or nested-Compose combinations and rejects every undeclared or out-of-bounds override. A successful result contains the effective immutable settings, the canonical preset digest, and the canonical effective-settings digest. Backend version changes alter the effective digest. The host must separately bind the reviewed provider release, connection revision, configuration digest, and current authority because they are outside this pure preset calculation.

`sandboxPresetDigest` hashes a validated preset with the package's canonical digest format. `validateCandidateSandboxPresetQualifications` requires current host-produced evidence for every declared provider and preset. Candidate evidence contains exactly SP01, SP02, SP03, SP05, SP07, and SP08. Its `releaseDigest` is the stable pre-verification release-input digest supplied by the host; this avoids a digest cycle because the stored release digest also covers the candidate report. `validateLiveSandboxPresetQualification` is the separate Ready assertion for one connection and effective settings digest. Live evidence contains SP01 through SP08, including real-workload SP04 and recovery/cleanup SP06. Missing, extra, duplicate, failed, skipped, expired, future-dated, or mismatched evidence fails closed.

Live qualification is connection state. It does not belong in `BuildEvidence`, and this package does not claim live SP04 or SP06 results. `CandidateVerificationReport.sandboxPresetQualifications` is optional for wire compatibility; the host assertion makes it mandatory when a manifest declares sandbox providers.

The production candidate verifier does not yet run the shared sandbox conformance harness. It therefore rejects every release that declares `sandboxProviders` with `sandbox_qualification_unavailable`. This is an intentional release gate: sandbox provider releases remain unusable until C06 supplies host-produced SP01, SP02, SP03, SP05, SP07, and SP08 evidence. Tests may inject evidence only to verify the later lifecycle boundaries; injected test evidence is not a support claim.

Tool and runtime method schemas support object, array, string, number, boolean, and null types; required fields; bounds; enum/const; alternatives; and local named references. Schema size, depth, reference expansion, and alternatives are bounded. Recursive and remote references are rejected. Patterns use the linear-time RE2JS engine; backreferences and unsupported RE2 syntax are rejected. Input and output must be bounded JSON data. Schemas never coerce values or add defaults.

The checked `src/wire-schema.json` is generated from `src/types.d.ts`. Run `bun run schema:generate` after changing data types, then `bun run schema:check` and `bun run build`. CI must run the schema check.

Runner operations receive immutable file data and host-issued IDs, never host paths or raw container options. `RunnerExecution` uses bounded newline-delimited JSON-RPC. `extension/discover` returns metadata. `extension/invoke` accepts `{name,input,context}`; `extension/dispatch` accepts `{method,input,context}`. `extension/cancel` accepts `{invocationId}`. Reverse RPC carries `{context,input}`. The host must revalidate the context against its active invocation registry and approved release before every effect.

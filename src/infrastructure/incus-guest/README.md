# Guest helper 0.1.0

Install `helper.py` in the guest at `/usr/local/libexec/ezharness-helper`, owned by root and executable by the configured guest user. Install Python 3. The guest image must create `/workspace` and `/var/lib/ezharness-helper`, both owned by that user; the state directory has mode `0700`. Host transport invokes the helper as that user, sends one JSON request on stdin, closes stdin, and reads one bounded JSON reply from stdout. A missing executable, nonzero exit, invalid reply, or version mismatch fails the provider request. `protocol.ts` exports the fixed path, version, source SHA-256, and bounded codec.

The request includes `version`, a host-derived `sandboxId`, the pinned `user`, `action`, and action fields. `hello` verifies the live guest user, workspace root, helper version, and boot ID. File paths and process cwd are workspace-relative; `.` selects `/workspace` for list/cwd. The helper opens each parent directory using `O_DIRECTORY | O_NOFOLLOW` relative to an existing directory descriptor. Reads and writes are binary-safe base64. A write is limited to 64 KiB and uses an atomic replacement plus a revision check. File deletion of a regular file or empty directory is supported; recursive deletion is currently rejected. Per-path helper locks serialize helper writes/removes. Direct writes by a process running in the workspace are outside those locks; the provider controller should enforce its writer lease.

Stable file locks live under `mutations/file-locks` in the private helper state directory, outside the checkout. Each lock identifies the sandbox, opened parent directory and filename. Keep these lock files while the sandbox exists: deleting one can let a new writer use a different inode while another writer still waits on the old lock. Helper edits and removals must leave no internal files in the Git checkout.

Process starts return a durable process ID and guest boot ID. A detached supervisor persists status and at most 1 MiB of framed stdout/stderr under the state directory. Output pages are limited to 64 KiB. The child receives a parent-death signal if its supervisor dies, and cancellation or timeout signals the entire child process group. A handle from another guest boot is rejected. A missing supervisor may leave a handle in `unknown`; the host must reconcile before reusing the writer lease.

`process.start`, `file.writeAtomic`, and `file.remove` require stable `requestId` and `idempotencyKey` fields supplied by the host operation. Process start derives its durable ID from both fields and the sandbox ID. Exact replay returns the saved handle; changed input under the same identity fails. File mutations record a pending journal entry before the effect and a completed result afterward. Exact completed replay returns the saved result. A pending entry remains unknown and cannot be retried as a new effect. The host must replay with the original request body, including the same process deadline; a new tool call uses a new operation identity.
